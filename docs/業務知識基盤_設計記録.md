## 0. プロジェクト名: Koto

- 名称は **Koto** に決定。由来: 本プロジェクトの二本柱である**言(こと)=ユビキタス言語(term)**と**事(こと)=業務イベント(event)**が同じ音に宿ることから。「DDDはヒト・モノ・コトのうちコトが重要」というユーザーの哲学をそのまま名前にしたもの。
- CLI・MCPサーバ名は `koto` を使う想定(例: MCP登録名 `koto`)。
- 検討した次点候補(記録として): **知層(Chisō)**=知識がdraft→approvedと堆積しrevisionsが層として残る構造の表現 / **還流(Kanryū)**=知識還流ループそのものだが名前としては説明的。
- 運用開始時、**名前自体を最初のtermレコードとして登録する**(title「Koto」、english_name「koto」、bodyに由来と指すもの)。プロジェクトの命名はユビキタス言語策定の第一号案件であり、知識基盤が自分自身の名前を自分に格納するところから運用を始める。

## 1. 目的・ビジョン

- AIエージェントに**要件定義 → 設計 → 実装 → リリースを丸投げ**できる仕組みを作る。
- そのために、毎回単発でブレストするのではなく、**業務知識(ドメイン)を都度蓄積**し、そこから最適な要件定義・設計を導出する「知識の蓄え場所」と「導出方法」を整備する。
- 業務に関する質問はAIに聞けば解決する状態を目指す。
- まずローカルで実験し、うまくいけばチーム共有(クラウド)へ。

全体像は3点セット: **①知識リポジトリ(中央DB) ②導出の仕組み(スキル/エージェント) ③還流ループ(作業のたびに知識を書き戻す)**。

## 2. 主要な決定事項と経緯

### 2.1 保存方式: Git+Markdown案 → 専用DB(中央管理)へ

- 初案はGit管理のMarkdownリポジトリだったが、ユーザー方針により**専用DB+ベクトルストアでの中央管理に決定**。
- ユーザーの見解: 一般企業でDDDの境界づけられたコンテキストごとに管理を分ける運用は難しい。**管理は1つに統一し、その中でコンテキストを分ける**(連邦型・管理分割には反対)。
- 設計上の注意: ベクトルストア**単体**では管理できない(検索手段であって管理単位・品質担保・履歴を持たない)。→ **構造化された知識レコードを持つDBに埋め込みを同居**させる。
- DB選定: **Postgres + PGroonga(日本語全文検索) + pgvector**。理由: ローカル(Docker)→クラウド(Supabase/RDS)が接続先差し替えで済む。
  - SQLite(+sqlite-vec+FTS5 trigram)も実験段階なら現実的。**MCP層がDBを隠蔽するので後から差し替え可能**(repository層の書き換えのみで閉じる)。libSQL/Tursoでクラウドまで行く道もある。
- 日本語検索の注意: Postgres標準のtsvectorは日本語に実用不可。PGroonga必須。

### 2.2 データモデル: 「チャンク」ではなく「知識レコード」

RAGにありがちな機械的チャンク分割はしない。**1概念=1レコード**の粒度。

- **type**: `term / rule / decision / requirement / faq / event`
- **多義語**: `(context, type, title)` 複合ユニーク。「注文」が受注と発注で別物なら、context違いの別レコードとして共存。
- **用語(term)の構造化**: 機械が使う項目だけカラムに出す。
  - `english_name`(コード・API・テーブルで使う正式名を1つに固定 → 命名規約として実装を統制)
  - `aliases`(`{name, kind: synonym|forbidden}`。forbidden=禁止表記。検索の表記揺れ吸収+レビューエージェントの警告に使う)
  - 定義・ルール・前提・背景は `body`(Markdown)のまま
- **関連**: `knowledge_relations(from_id, to_id, label, cardinality)` のエッジテーブル。
  - **概念マップ・業務フロー・状態遷移図は保守せず、ここから都度導出する**(手書きマップは乖離するため)。
  - ラベル規約: モノ・用語間=意味ラベル(「含む」「引当」「同名別概念」等) / コト間=「先行」「取消」 / コト→モノ=「対象」
- **履歴**: 更新トリガで `knowledge_revisions` に全変更を自動保存(Gitの差分・履歴の代替)。削除は物理削除せず `deprecated`+後継エッジ。
- レコードサイズ運用ルール: 本文が画面1枚を超えたら分割を提案。

### 2.3 DDDとの関係(ユーザーの重要な観点)

- ユーザーの見解: **DDDは「ヒト・モノ・コト」のうちコトが重要**。← 全面同意で設計に反映。
- ルールも状態もコトに従属する(「受注ステータス」はコトの結果の射影)。
- **event型**は他typeより構造を持たせる: 本文テンプレート「概要 / アクター(誰が起こすか) / 対象(何に対して) / 事前条件 / 事後条件 / 取消・失敗 / 順序・タイミング」。
- **アグリゲート境界の導出**が可能: 「トランザクションで即時に守る不変条件の範囲=アグリゲート」。ruleの整合性要件(即時整合か結果整合か)+relationsから設計スキルが導出する。→ ruleに即時/結果整合の記録が必要(未実装、bodyの規約でも可)。
- **ヒアリングはコト起点(軽量イベントストーミング)**: 「一日の業務で何が起きるか」を時系列で聞き、出てきたコトから用語を逆引き。定型の問い:「その前には何が起きますか」「失敗・取消できますか」「誰がやりますか」。
- **注意**: コト中心の知識化とイベントソーシング実装は別物。設計導出で安易にイベントソーシングを提案しない(この方針を最初のdecisionレコードとして登録する)。

### 2.4 承認フロー(還流の品質ゲート)

- エージェントの書き込みは**すべて `status=draft` + `needs_review=true`** で入る。人の承認で `approved`。承認済みだけが検索のデフォルト対象。
- **判断の非対称性**:
  - 読み(検索)=副作用ゼロ → 「迷ったら読む」。本命は仕組みで自動化(後述の層3)。
  - 書き(propose)= エージェントの基準は「正しいか」ではなく「**新規性があり再利用されうるか**」。正しさの判定は人のゲートが引き受ける。
- **書きの判断は読みから派生する3分岐**(propose前に必ず検索):
  1. ヒットなし → `propose_knowledge`(新規draft)
  2. 矛盾・不足 → `propose_update`(更新提案)
  3. 一致 → 登録しない(重複を作らない)
- 溜めないもの: タスク限りの一時情報 / 一般的なIT知識 / 推測(推測は本文に混ぜずreview_notesへ)。
- 近似重複検出: 同名・別名一致 + 埋め込み類似(≥0.82)を自動検出しreview_notesに記録。統合判断は人。
- レビュー運用の現実解: CLI直より**エージェントとの対話でレビュー**(「レビュー待ちを見せて」→会話で修正→承認)。人間は判断だけ。
- 更新の現仕様: approvedへの更新は**即時反映+needs_review**(楽観方式、revisionsで巻き戻し可)。チーム共有時は「承認まで旧版を見せる」二重化に格上げ(Phase 2課題)。

### 2.5 判定権限の分散のデータ化(contextsマスタ)

- 「人のレビュー」は一枚岩ではない。**知識の正しさを判定できる人は知識の種類ごとに違う**(税理士は一例: 法令=税理士/弁護士、業務ルール=オーナー部署、技術規約=テックリード…)。
- 置き場所は中央、**判定権限は本質的に分散** → これをデータで表現:
  - `contexts` マスタ: `name / description / owner(承認責任者) / expert(外部専門家の種別)`
  - 未知のcontextはpropose時に自動登録(owner未設定として可視化、後で埋める)
  - Phase 2のレビュー通知ルーティング(Slack等)の根拠になる
  - **「誰が判定できるか」自体が組織のドメイン知識** → `upsert_context` ツールでヒアリングから埋まる
- **検証レベル3段階**: `none(未検証) / internal(社内確認済) / expert(専門家確認済)`
  - approveでinternal、`verify <id> expert` で引き上げ
  - **内容が更新されたら自動でnoneに戻る**(専門家確認は旧版に対するもの)
  - **不確かさの伝搬**: 検索結果に検証レベルが含まれ、expert未満の法令系知識に依拠した成果物には注記を引き継ぐ(search_knowledgeのツール説明に明記済み)

### 2.6 知識の初期投入(3導線)

まとまった戦略はまだない状態から、以下で開始:

1. **導線1: 文書抽出** — 仕様書・WikiをLLMで抽出しdraft投入。社内文書は古い・間違っている前提で全て「仮説」扱い。sourceに文書パス・チャンク位置を記録。
2. **導線2: 部署ヒアリング** — 導線1で作った仮説の辞書をぶつける形式(ゼロベースは発散する)。コト起点で進める。①エージェントと直接対話(質が高い) or ②議事録を後から抽出。
3. **導線3: 調査由来** — ふわっとした記憶を仮説として受け、Web調査(一次情報優先)→差分を人に提示→出典URL+確認日つきでdraft化。
   - 実例で検証済み: 「電子マネー決済は電子で払ったことを明示…」→ クレジットカードは正しい(国税庁: 信用取引で金銭受領事実なし、「クレジットカード利用」記載で印紙不要。記載なしなら5万円以上で印紙必要)。ただし**電子マネー/コード決済への一般化に罠**(受領事実の有無で課税判定が分かれ、決済サービス名の表記だけでは不十分な場合がある=国税庁のコード決済見解)。→ ふわっと記憶をそのまま登録せず裏取り→draft→人の確認、というフローの価値の実証。
   - 格納するのは法令の複製ではなく「**自社の業務がどう振る舞うか+根拠リンク**」。`source.kind="research"` には確認日必須、棚卸しの重点対象。税務等の最終確認は専門家へ(検証レベルexpertの出番)。
- コンテキスト割り当ては当面「部署名を仮タグ」でよい(中央DBなので後で一括振り直し可能)。
- パイロット: 全社ではなく「文書がまとまっている1領域+協力的な1部署」から。

### 2.7 エージェントとのシームレスな接続(「MCPを繋いでも触ってくれない」問題)

効き目の弱い順に3層。シームレスさの正体は3層の併用。

- **層1(弱): 判断に任せる** — ツール説明の命令形+CLAUDE.mdに利用規約(検索必須・english_name命名・還流)。必要だが不十分。
- **層2(中): 手順に組み込む** — 要件定義/設計スキルの手順1に検索、最終手順に還流を固定。「①list_contextsで地図 → ②search_knowledge → ③関連展開で収集 → ④作業 → ⑤propose_knowledge」。superpowersパイプライン(brainstorming→writing-plans→TDD→review)の前段に接続。スラッシュコマンド化。
- **層3(強): 仕組みで強制(pull→push)** — Claude Codeフック(モデル判断を経由しない決定論):
  - SessionStart: コア知識(コンテキスト一覧+最重要用語)を注入(「常時ロードするコア知識」の実装)
  - UserPromptSubmit: 入力を毎回自動ハイブリッド検索し上位ヒットを文脈に添付(会話常駐RAG。MCPツールは深掘り用に残す)
  - Stop: タスク終了時に還流(propose)を確認
  - PostToolUse(Edit/Write): forbidden別名との突き合わせで命名警告
- **計測**: MCPサーバにツール呼び出しログ(1テーブル)→「検索せず設計を始めたセッション」「還流ゼロの週」を可視化。成功基準判定の根拠にもなる。

### 2.8 検索・導出の仕様

- ハイブリッド検索: PGroongaキーワード + pgvectorベクトルを**RRF(順位融合)**で統合。context/type/statusフィルタ。埋め込み無効時はキーワードのみにフォールバック。
- 関連展開: デフォルト1ホップ、要件定義など広く取る場面のみ2ホップ。
- 2層構え: 常時ロードするコア知識(コンテキストマップ+最重要用語)+オンデマンド検索。
- 埋め込み: OpenAI text-embedding-3-small(1536次元)。`EMBEDDING_PROVIDER=none` で無効化可。
- 抽出モデル: `claude-sonnet-4-6`(env `EXTRACT_MODEL`)。

### 2.9 初期構成は課金ゼロ・インポート主経路はエージェント対話(2026-08-09追記)

- ユーザー方針: **初期構成では課金形態を気にしない作りにする**。API キー必須の機能をデフォルト経路に置かない。
- **文書インポートの主経路を「エージェント対話 + MCP」に変更**。「この文書を koto に取り込んで」と頼めば、抽出はエージェント自身(ユーザーのサブスクで動く Claude)が行い、`propose_knowledge` で draft 投入する。koto 自身は LLM を呼ばない。抽出の型(コト起点・event 定型見出し・推測の分離・source 形式)はリポジトリ同梱スキル `skills/koto-import/` が与える(`.claude/skills/` からシンボリックリンク)。
- 従来のバッチ CLI(`pnpm run import`)は**オプション経路に降格**: 大量一括処理・API Only 環境向け。claude CLI(サブスク)優先、`ANTHROPIC_API_KEY` フォールバック。
- **埋め込みはデフォルト無効**(`EMBEDDING_PROVIDER` のデフォルトを `none` に変更)。`EMBEDDING_PROVIDER=openai` + キーの明示オプトインでのみ有効。埋め込みなしでもキーワード検索(PGroonga)+ aliases + エージェントのクエリ言い換えで実用になる想定。縮退するのは近似重複検出(同名・別名一致のみになる)。
- 将来、意味検索が必要になった場合の課金なし選択肢として Ollama + ローカル埋め込みモデル(bge-m3 等)を検討(次元数変更のマイグレーションが必要)。

## 3. 仮決め事項(実験中の前提)

- 外部API利用OK(埋め込み・抽出)。本番前に再検討。
- 承認者はユーザー1人。エージェント投入は自動(全てdraft)、承認は人。
- **Phase 1成功基準**: 過去に実際にやった要件定義・設計判断を1つ選び、DB内の知識だけを渡したエージェントが当時と同等の要件定義書を再現できるか。通れば知識の粒度と検索が機能している証拠 → チーム共有へ進む。

3. **ubiquitous-languageスキル改修**: 最終ステップのMarkdown出力を `propose_knowledge` 呼び出しに差し替え。モードBのコト起点(イベントストーミング風)変形版を作る。
4. **要件定義/設計スキルの新規作成**: 冒頭に知識検索・末尾に還流を固定。設計スキルにはアグリゲート導出手順(即時整合の範囲判定)。ruleへの即時/結果整合の記録規約もここで導入。
5. **棚卸しジョブ**: 矛盾・重複・陳腐化の定期検出。`source.kind="research"` の再調査(1年未確認でneeds_review)。
6. **Phase 2(チーム共有)**: DBをSupabase/RDSへ、MCPをリモート(HTTP+OAuth)へ。レビューのSlack通知/UI化(ルーティング根拠=contextsマスタのowner)。approvedレコード更新の二重化(承認まで旧版を見せる)。非エンジニア向けNotion同期の検討。
7. **Phase 3(パイプライン統合)**: 要件定義〜リリースの自動化。テスト・コードレビュー・リリース承認の3検証ゲートは人間に残す(丸投げが崩壊するのは生成側でなく検証の不在)。

## 6. ユーザーの方針・こだわり(セッション引き継ぎ用)

- 中央管理派: 管理(置き場所)の分割に反対。1つの管理の中でコンテキストを分けるのは賛成。
- 一般企業でDDDの境界づけられたコンテキスト運用は難しいという現実認識。
- DDDでは「ヒト・モノ・コト」のうち**コト重視**。
- 実験→チーム共有の段階的展開(ローカルは実験段階の話)。
- 議論スタイル: 提案に対して前提を疑う指摘をする。デフォルト案は置いてよいが、状況依存の判断は質問で確認してから進めるのが良い。
