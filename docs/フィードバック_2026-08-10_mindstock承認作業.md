# koto フィードバック — mindstock/resident 承認作業から

> 記録日: 2026-08-10
> 出所: mindstock の `resident` コンテキストに import された draft 26 件を、Claude Code 上で 1 件ずつ承認していく作業。10 件承認したところで「技術的な記述に偏りすぎている」という違和感が出たため、承認作業を中断して koto 自体の粗探しに切り替えた。
> 検証環境: `koto-db-1`(ローカル Docker)、`EMBEDDING_PROVIDER=none`、knowledge 231 件。

## 総評

コンセプト(コト中心・承認ゲート・contexts による判定権限の分散)は実際に触っても筋が良い。特に **1 件ずつ人が見る運用は機能した** — 承認作業の中で「1 居住者は複数プロバイダを持てるのか」「`Registered` はセッションが登録されるという意味ではない」といった、元の文書には無い理解が実際に得られ、その場で本文に反映できた。ゲートが知識を作っている。

一方で、実害のある問題が 2 系統見つかった。

1. **検索の並び順が実際には機能していない**(後述 1.1)。知識基盤の価値は「エージェントが設計前に検索する」ことに乗っているので、ここは他のどの項目よりも先に直す価値がある。
2. **ユビキタス言語としての構造が機能していない**(後述 2)。`english_name` が実装識別子の写しになっており、同一概念が context をまたいで重複し(13 グループ)、`居住者` と `住人` のように直接矛盾する登録まで生まれている。禁止表記(`forbidden`)は 231 件で一度も使われていない。

2 は「ユビキタス言語を統制する」という koto の目的そのものに関わるため、個別の不具合修正ではなく **設計からの見直しが必要**と判断した。

以下、重い順。

---

## 1. 実害のある不具合

### 1.1 【最重要】キーワード検索の並び順が全く効いていない

`pgroonga_score()` が全行 0 を返しており、**キーワード検索の順位付けが完全に無意味**になっている。

実測:

```
koto=# select title, pgroonga_score(tableoid, ctid) as score
       from knowledge where search_text &@~ '表示名' and status='approved' order by score desc;
       title        | score
--------------------+-------
 居住者プロフィール |     0
 居住者             |     0
 表示名             |     0
 表示名履歴         |     0
```

「表示名」で検索して、`表示名` そのものより `居住者プロフィール` が上に来ている。

原因はクエリプランである。PGroonga の `pgroonga_score()` は **Bitmap Heap Scan では 0 を返す**。プランナは現状の行数だと bitmap scan を選ぶ:

```
koto=# explain (costs off) select title from knowledge where search_text &@~ '表示名';
 Bitmap Heap Scan on knowledge
   Recheck Cond: (search_text &@~ '表示名'::text)
   ->  Bitmap Index Scan on idx_knowledge_fulltext
```

`enable_bitmapscan=off` にすると、期待どおりのスコアが返る:

```
koto=# set enable_bitmapscan=off;
koto=# select title, pgroonga_score(tableoid,ctid) s from knowledge where search_text &@~ '表示名' order by s desc limit 4;
   title    | s
------------+---
 表示名変更 | 9
 表示名履歴 | 5
 居住者登録 | 4
 住人登録   | 4
```

**影響範囲は両経路。** `packages/core/src/search.ts` のフォールバック経路(埋め込み無効時)は `order by pgroonga_score(...)` で直接並べているので順序がランダム。ハイブリッド経路も `kw` CTE が `row_number() over (order by pgroonga_score(...) desc)` なので、RRF に入るキーワード側の順位が丸ごとノイズになる。

**しかも既定構成が直撃する。** 設計記録 2.9 で `EMBEDDING_PROVIDER` の既定を `none` にしたため、標準インストールではフォールバック経路(キーワードのみ)が動く。つまり **既定の koto には実質ランキングが無い**。`limit 10` は「マッチした中から任意の 10 件」を返している。

さらに `limit 50` / `limit 10` による打ち切りが順不同に効くので、**関連する知識が静かに欠落する**。エージェントは「該当なし」より質の悪い「一部だけ返ってきた」を受け取る。

対応案:
- 検索クエリを投げる接続で `SET enable_bitmapscan = off` する(セッション単位。最小の修正)
- または `pgroonga_score` に依存せず、明示的なスコア取得方法(`pgroonga_command` 等)に切り替える
- いずれにせよ **順位が意味を持つことを検証するテストを足す**。「`表示名` 検索で `表示名` が 1 位」程度の assertion があればこの不具合は入らなかった

## 2. ユビキタス言語としての構造が機能していない

この節は個別の不具合ではなく、**koto の目的そのものが達成できていない**という指摘。承認作業を止めたあと、231 件全体を調べて判明した。結論として、ここは設計から見直す。

### 2.1 `english_name` が「日本語名の英訳」ではなく実装識別子の写しになっている

設計記録 2.2 は `english_name` を「コード・API・テーブルで使う正式名を **1 つに固定** → 命名規約として実装を統制」と位置づけ、`koto-import` スキルは「**スペース禁止、snake_case**。例: `sales_order`, `credit_check`」と定めている。

実際に入っている値を種類別に分けるとこうなる。

| 識別子の種類 | 実例 |
|---|---|
| 型名 | `Resident` `Household` `Quantity` `CatalogItem` |
| ネスト型 | `MindstockSession.Unregistered` `Barcode.Linked` |
| テーブル名 | `resident_display_names` `product_catalog_links` |
| Exposed の Table オブジェクト | `ProductBarcodesTable` |
| 例外クラス | `DuplicateJanException` |
| Repository interface | `ExternalProductRepository` |
| メソッド・関数名 | `lookupByJan` `whoami` `rename` `runGuarded` `canManageMaster` |
| フィールド・引数名 | `callId` `actor` |
| Controller | `ReauthController` |

**用語「外部商品情報」の english_name が `ExternalProductRepository` になっている**のが象徴的で、概念の英語名ではなく「その概念を扱う interface の名前」が入っている。snake_case 規約は最初から守られていない(守れない — Kotlin の型は PascalCase、テーブルは snake_case、メソッドは camelCase)。

type ごとの充足率も偏っている。

| type | 全件 | english_name あり |
|---|---|---|
| term | 94 | 84(89%) |
| event | 62 | 21(34%) |
| rule | 75 | 8(11%) |

事実上 term 専用フィールドになっている。しかも event の値は `register` / `whoami` / `rename` で、コトの英語名ではなく **その操作を実装した RPC メソッド名**。rule の 8 件も `SessionGuard`(ガード関数)`ProductName`(VO クラス)など、ルールの名前ではなく「そのルールを実装している場所」が入っている。

**決定した方針**: `english_name` は **`title`(日本語名)の英訳**とする。クラス名・ファイル名・テーブル名・メソッド名は入れない。

理由: 実装は雑に書かれることもあれば、実装都合で概念と一致しない命名になることもある。そこに english_name を結びつけていると、**そういうケースが出たときにカバーできなくなる**。ユビキタス言語は実装から独立して成立していなければならず、実装名を写すのは依存の向きが逆。

反映が必要な箇所:
- 設計記録 2.2 の「コード・API・テーブルで使う正式名」という定義
- `koto-import` スキルの snake_case 規約と例示
- `propose_knowledge` / `propose_update` の `english_name` の description(現在「コード・テーブル・APIで使う正式英語名」)
- type ごとに english_name を求めるか(rule に英語名を要求する意味があるか)

### 2.2 同一概念が context をまたいで重複している(13 グループ)

同じ `english_name` を持つレコードが複数ある。

| english_name | 重複しているレコード |
|---|---|
| `Resident` | `resident/居住者` と `session/住人` |
| `MindstockSession.Registered` | `resident/居住者登録済みの接続` と `session/登録済みセッション` |
| `MindstockSession.Unregistered` | `resident/居住者未登録の接続` と `session/未登録セッション` |
| `AuthIdentity` | `resident/認証アイデンティティ` と `session/認証アイデンティティ` |
| `Barcode` | `barcode/バーコード` `inventory/バーコード` `inventory/商品バーコード`(3 件) |
| `CatalogItem` | `barcode/カタログ品目` と `catalog/カタログ商品` |
| `Jan` | `barcode/JANコード` と `catalog/JAN` |
| `lookupByJan` | `barcode/JAN照会` と `catalog/カタログ商品のJAN照会` |
| `ExternalProductRepository` | `barcode/外部商品照会` と `catalog/外部商品情報` |
| `register` | `catalog/外部商品情報のカタログ取り込み` と `resident/居住者登録` |
| `ProductName` | `inventory/商品名` と `inventory/商品名の制約と変更不可` |
| `SessionGuard` | `session/登録ガード` と `session/登録済み必須のフェイルクローズ` |

**`居住者` と `住人` は直接矛盾している。**

```
resident | 居住者 | [{"synonym": "Resident"}, {"synonym": "住人"}]   ← 住人は別名だと宣言
session  | 住人   | [{"synonym": "resident"}]                       ← 住人が独立した用語として存在
```

一方は「住人は居住者の別名」と言い、もう一方は「住人」を独立した用語として登録している。ユビキタス言語基盤として、これが最も避けたかった状態のはず。

**なぜ検出されなかったか。** `findDuplicates` が同一 context 内しか見ていない(`packages/core/src/knowledge.ts:28-36`):

```sql
where context = $2
  and (lower(title) = lower($1) or exists (... aliases ...))
```

context 横断で効くのは埋め込み類似度の方だけだが、`EMBEDDING_PROVIDER` の既定は `none`。つまり **既定構成では context 横断の重複検出が完全に無効**。

**設計の想定と逆の事故が起きている。** 設計記録 2.2 が想定したのは「**多義語** — 同じ言葉が context によって別物(受注の注文 / 発注の注文)」で、これは `(context, type, title)` の複合ユニークで正しく扱える。実際に起きたのは逆の「**同義語** — 別の言葉が同じ物」で、こちらへの防御が一切ない。

**構造的な原因は 1 context = 1 出典文書だったこと。**

```
barcode(27) ← barcode.md      catalog(21) ← catalog.md
household(41) ← household.md  inventory(72) ← inventory.md
resident(26) ← resident.md    session(42) ← session.md
```

6 つの文書が概念的に重なっているのに、文書ごとに独立して import され、突き合わせが行われていない。`session` は実質 `resident` の重複コンテキストになっている。

### 2.3 `term` に業務概念でないものが混ざっている

`term` は「言 = ユビキタス言語の用語」(設計記録 0 節)。だが実際には実装構造物が term として登録されている。

| title | english_name | 実体 |
|---|---|---|
| 表示名履歴 | `resident_display_names` | テーブル |
| 商品バーコード行 | `ProductBarcodesTable` | Exposed の Table オブジェクト |
| 登録ガード | `SessionGuard` | ガード関数 |
| トークン保管 | `TokenStore` | フロントエンドの保管クラス |
| 呼び出し ID | `callId` | セッションのフィールド |
| アプリサブプロトコル | `AppSubprotocol` | WebSocket のサブプロトコル文字列 |
| 起動分岐 | `AuthState` | フロントエンドの状態 enum |
| 再認証 | `ReauthController` | フロントエンドのコントローラ |

これらは業務の語彙ではないので、そもそも term として登録すべきでなかった。2.1 と同じ根(実装を写している)から来ている。

### 2.4 `title` の粒度・表記が統一されていない

- **スペースの有無がゆれている**: `世帯 ID` `呼び出し ID` に対し `居住者ID` `商品ID` `カタログ商品ID`
- **rule の title が文章になっている context がある**: `session` だけ「JWT の完全検証は接続確立時の 1 回のみ、以後は有効期限だけを都度チェック」「住人検索のインフラ障害時は未登録へ降格させない」。他の context は「商品名の制約と変更不可」のような名詞句

`title` は `(context, type, title)` 複合ユニークのキーの一部なので、表記ゆれはそのまま重複の温床になる。event については「出来事の名詞化」という規約がスキルにあるが、**term / rule の title 規約が無い**。

### 2.5 `forbidden` 別名が 1 件も使われていない

```
forbidden な alias の総数: 0 / 231 件
```

「使ってはいけない表記」は設計の柱のひとつで、設計記録 2.2 は「検索の表記揺れ吸収 + **レビューエージェントの警告に使う**」、2.7 層3 は「PostToolUse(Edit/Write): forbidden 別名との突き合わせで命名警告」としている。231 件で一度も使われていない。

**`住人` はまさに forbidden の第一号候補だった。** 「居住者」に統一し「住人」を forbidden にしていれば 2.2 の矛盾は起きなかった。機能が存在しても、それを使う判断をエージェントに促す仕組みが無い。

### 2.6 インポート元の資料を作る導線が無い

現状のスキルは `skills/koto-import/`(**既存文書を koto に入れる**手順)の 1 本だけ。だが今回の問題の多くは、**入れる前の資料の作られ方**に起因している。

- `docs/knowledge/*.md` はコードから起こした資料なので、決定理由(なぜ 100 文字なのか)が原理的に含まれない
- 6 文書が独立に書かれたため、文書間で概念が重複した(2.2)
- 「業務知識」と「実装詳細」の切り分け基準が資料側に無かったため、技術記述が大量に混入した(3.1)

**決定した方針**: 一定のルールに基づいて **インポート元の資料を作らせるスキル**を用意する。koto-import の上流にあたる導線で、少なくとも次を規定する必要がある。

- 概念の粒度と title の付け方(term / rule / event それぞれ)
- 実装識別子を書かない(english_name は日本語名の英訳 — 2.1)
- 既存の koto レコードと突き合わせ、同義語を作らない(2.2)
- 決定と理由を書き、手段は書かない(3.1)
- 資料をまたいで重複する概念の扱い(どちらの context に置くか)

## 3. コンセプト・運用上の問題

### 3.1 「何を入れるか」の基準が、実運用に耐える粒度で定義されていない

`koto-import` スキルの抽出規約は「この業務に固有の概念だけを抽出する。一般的な IT 用語・ツール名・ファイル形式は拾わない」と言う。これは **除外の基準** であって、**採否の基準ではない**。

実際に起きたこと: 出典が「コードから起こした業務知識資料」だったため、規約上は「業務固有」を通過する技術記述が大量に混入した。例:

> 「現在の表示名」は同一居住者の中で ID が最大の行として求める(`rowNumber().partitionBy(residentId).orderBy(id DESC)` を `rn = 1` で絞る)

これは mindstock 固有ではあるが、業務知識ではない。承認作業で出た基準はこうだった:

| 記述 | 種別 | 判定 |
|---|---|---|
| 表示名は変更できる | 決定 | 残す |
| 変更しても過去の記録が残る | 業務上の性質 | 残す |
| 1〜100 文字 | 決定された制約値 | 残す |
| **なぜ 100 文字なのか** | 決定の理由 | **最も残すべき。だがどこにも無い** |
| 同名の居住者が複数いてよい | 決定 | 残す |
| ID 最大の行として求める | 手段 | 落とす |
| append-only テーブルである | 手段 | 落とす |

**提案: 抽出規約に「決定と理由は残す、手段は落とす」という軸を足す。** 理由は 3 つ。(a) 手段はコードが変わると腐り、エージェントはコードと koto の食い違いを判定できない。(b) 手段はコードを読めば常に正確に分かる。(c) 手段が混ざると本当の信号が埋もれる。

**あわせて指摘したいこと**: 上の表で「最も残すべき」とした〈なぜ〉が、コード由来の 26 件にはほぼ一件も含まれていなかった。導線1(文書抽出)は構造を写すのは得意だが、**決定理由は原理的に拾えない**。導線1 だけで基盤を作ると「コードの劣化コピー」になる。導線2(ヒアリング)との併用が前提であることを、スキル側にも明記した方がよい。

### 3.2 知識の「正」がどこにあるかが決まっていない

今回の 26 件の `source.ref` はすべて `docs/knowledge/resident.md`(mindstock 側のファイル)。koto 側で本文を直しても、**その文書を再 import すれば技術記述が戻ってくる**。

- koto が正なら、import 後に元文書を捨てるか「import 済み・以後 koto が正」と印を付ける運用が要る
- 文書が正なら、koto での修正は無意味なので、修正は文書側に還流させる導線が要る

設計記録 2.6 は初期投入の導線を 3 つ定義しているが、**2 回目以降の import(再取り込み)の扱いが未定義**。`(context, type, title)` の複合ユニークがあるので `propose_knowledge` は失敗するはずだが、その時エージェントが何をすべきかがスキルに書かれていない。

### 3.3 `review_notes` が 3 つの役割を兼ねていて、承認者が何をすべきか判断できない

現状 `review_notes` に混在しているもの:

1. **業務エキスパートに聞くべき質問** — 「退会・削除機能を将来提供する予定があるか」
2. **実装レビュー指摘** — 「INSERT した行を DB から読み戻さずメモリ上で組み立てる実装は、プロジェクト規約から外れており…」
3. **更新提案のメモ** — `proposeUpdate` が `更新提案: <note>` を追記する
4. (加えて)重複候補の自動検出結果

2 は koto の責務外(コードレビューの話)であり、承認者はそれに対して承認も却下もできない。1 と 3 は性質がまるで違うのに同じ欄に積まれる。

実例(承認後のレコード):

```
表示名履歴 | approved | 要確認: 過去の表示名を業務上参照する要件があるかは実装から読み取れない。
                       現状、履歴を読み出す経路は存在しない。
                     / 更新提案: SQL の実装詳細(rowNumber().partitionBy(residentId)…
```

**提案**: 少なくとも「未解決の確認事項」と「レビュー履歴」を分ける。前者は解決したらクリアできる必要がある(次項)。

## 4. ツール仕様の問題

### 4.1 承認しても「要確認」が消えず、解決したことを記録できない

`approve()` は `needs_review = false` にするだけで `review_notes` に触らない(`packages/core/src/knowledge.ts:233-245`)。結果、**承認済みレコードに「要確認: …」が永久に残る**。

実測(resident の承認済み 10 件):

```
居住者           | approved | 要確認: 「認証情報を持たない薄い集約にする」という設計意図は…
認証プロバイダ   | approved | 要確認: ZITADEL 以外のプロバイダを将来追加する想定があるか…
表示名履歴       | approved | 要確認: 過去の表示名を業務上参照する要件があるかは…
```

`get_knowledge` はこれをそのまま返すので、後からこのレコードを読むエージェントは「未解決の確認事項がある」と受け取る。実際には人が見て承認済みである。**承認の意味が伝わらない。**

### 4.2 `approve_knowledge` に理由欄が無い(`reject` と非対称)

`reject_knowledge` には `reason`(必須)があり、ツール説明も「この理由自体が後から参照される知識になる」と言っている。**承認側にそれが無い。**

今回の作業では、承認のたびにコードを読んで裏を取った — `DisplayName.kt` の `requireTrimmedWithin(100)`、`V1__init.sql` の `UNIQUE (provider, subject)`、`allowUnregistered` が 2 箇所しかないこと、等。**この検証の記録が一切残らない。** 半年後に「この知識は何を根拠に承認されたのか」を辿る手段が無く、再検証は一からになる。

却下理由が知識になるなら、承認根拠も同じかそれ以上に知識である。`approve_knowledge` に任意の `note` を足し、`verified_by` / `verified_at` と並べて残すべき。

### 4.3 `get_pending_reviews` が `review_notes` を無言で 200 文字に切る

`left(coalesce(review_notes, ''), 200)`(`knowledge.ts:321`)。省略記号も「切り詰めた」印も付かない。

実際に見えたもの:

> …また登録時に INSERT した行を DB から読み戻さずメモリ上で `Resident` を組み立てて返す実装は、プロジェクト規約(INSERT 後は読み戻

文が途中で切れている。`total` と `items` の件数不一致には丁寧な注意書きがあるのに、こちらは無言。せめて `…` を付けるか、切り詰めたことをフラグで返すべき。

### 4.4 `contexts` の owner が空のまま承認できてしまう

設計記録 2.5 の中核は「知識の正しさを判定できる人は知識の種類ごとに違う」で、それを `contexts.owner` でデータ化する設計。しかし実際は:

```
resident  | description: null | owner: null | expert: null | draft: 26
inventory | description: null | owner: null | expert: null | draft: 72
```

**owner が null のまま 10 件承認できた。** 誰も「承認責任者」に指定されていない領域の知識を、誰でも承認できる。`KOTO_REVIEWER` の値がそのまま `verified_by` に入るだけで、それが owner と一致するかの検査は無い。

実験段階(承認者 1 人)では実害が無いが、チーム共有に進む前に、少なくとも「owner 未設定のコンテキストで承認しようとしたら警告する」程度は要る。設計の中核概念が、実装では単なる自由記述メモになっている。

### 4.5 承認待ちの通し番号が保てず、作業の追跡がしづらい

`get_pending_reviews` は承認するたびに結果から消える。26 件を「1 件ずつ」処理する場合、進捗を追うには自分で通し番号を持つしかない。実際、承認を進めた後に一覧を取り直したところ番号がずれ、**別のレコードの ID を掴んで取得してしまった**(実行前に気づいたが、`approve_knowledge` を呼んでいたら誤承認していた)。

`approve_knowledge` は確認ダイアログに本文を出すので最終防波堤はある。ただ、レビュー作業を「セッション」として扱う概念(開始時に対象を確定し、進捗を持つ)があると事故が減る。

## 5. 環境・エラーメッセージ

### 5.1 `DATABASE_URL` が壊れていてもフォールバックが効かず、原因が分からないエラーが出る

`~/.claude.json` の koto MCP 設定で `DATABASE_URL` の値が `...`(プレースホルダのまま)になっていた。このとき出たエラー:

```
エラー: getaddrinfo EAI_AGAIN base
```

ホスト名 `base` はどこにも書いていないので、原因の見当が付かない。追跡すると:

- `pg` は接続文字列を `new URL(str, "postgres://base")` で解釈する。`...` は相対パス扱いになり、ホストが `base` になる
- koto 側のフォールバックは `process.env.DATABASE_URL ?? "postgres://koto:koto@localhost:5432/koto"`。`??` は **null/undefined のみ**を拾うので、`...` のようなゴミ値では発動しない

**提案**: 起動時に `DATABASE_URL` を `new URL()` で検証し、パースできない/ホストが取れない場合は「DATABASE_URL の形式が不正です(例: `postgres://koto:koto@localhost:5432/koto`)」と明示するか、フォールバックを効かせる。MCP は接続成功扱いになり、最初のツール呼び出しで初めて失敗するので、余計に原因が見えにくい。

## 6. 良かった点(残すべきもの)

- **1 件ずつ人が見る承認フローは実際に機能した。** 26 件のうち少なくとも 4 件で、元の文書に無い理解が承認作業中に得られ、その場で本文へ反映できた。「エージェントが投入し、人が判定する」の非対称性は正しい。
- **`review_notes` に要確認を分離する規約は効いた。** 「1 居住者が複数プロバイダを持てるか」という疑問は review_notes 由来ではなくユーザーの直感から出たが、review_notes があったおかげで「本文は事実、notes は疑問」という読み分けが最初からできた。
- **`approve_knowledge` の確認ダイアログに本文が出るのは正しい。** ID 取り違え(4.5)の最終防波堤になっている。
- **`propose_update` が履歴を自動で残す**ので、書き換えを躊躇せずに済んだ。20 revision 記録済み。
- **`get_pending_reviews` の `total` に関するツール説明**(「items より多い場合は打ち切られている、これで全部と報告するな」)は、エージェントの誤報告を実際に防ぐ書き方になっている。他のツール説明もこの水準に揃えるとよい。
