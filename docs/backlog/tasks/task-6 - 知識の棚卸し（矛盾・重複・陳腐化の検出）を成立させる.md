## 位置づけ

設計記録 5 の未着手項目。期待されている仕事は 4 つ。

- 矛盾の検出
- 重複の検出。特に english_name の英訳ゆれ（resident / inhabitant）。2026-08-10 の追記で、同一性キーにした代償としてすり抜けるので棚卸しで事後検出する、と明記された意図的な後始末
- 陳腐化の検出。調査由来（source.kind=research）を 1 年未確認で要レビューに戻す
- 実装は何も無い。常駐しているのは日次バックアップのコンテナだけ

## 先に決めないと成立しないこと（入力メタデータが存在しない）

research という文字列はスキルにもコードにも一度も出てこない。設計記録と README にしか無い。導線3（調査由来）のスキルが作られていないため。

- source.kind=research を書く経路が無く、重点対象を識別できない
- 確認日のキー名が決まっていない。スキルが定めているのは imported_at（取り込んだ日）だけで、一次情報を確認した日ではない
- source は jsonb で形式の検証が無い（propose_knowledge の入力型も任意のオブジェクト）
- verified_at は検証レベルを設定した時刻であり、別物
- propose_update に source を渡す引数が無いため、再取り込みしても source は初回のまま

## ジョブではなくエージェント導線にすべきか

英訳ゆれは文字列一致では拾えず、埋め込みは既定で無効。つまり SQL のバッチでは、棚卸しに期待されている仕事の中心が拾えない。
koto 自身は LLM を呼ばない（設計記録 2.9）という原則とあわせると、棚卸しもスキルとして人が起動する導線にするのが筋に見える。
加えて koto には定期実行の担い手がいない。MCP サーバは stdio で呼ばれたときだけ動く常駐しないプロセス。定期実行を置くなら担い手を決める必要がある。

## 実装時の罠

1. 要レビューを立てるだけで履歴が増える。更新トリガに条件節が無いため、内容が変わらない UPDATE でも knowledge_revisions にレコード全体が 1 行積まれる。定期で回すと内容の変わっていない履歴でノイズだらけになる
2. 承認済みに要レビューを立てても検索には出続ける（TASK-1 と同じ構造）。棚卸しが大量に印を付けると、レビュー待ちが埋まり（既定 100 件で打ち切り）通常のレビューが埋もれる

## 決めること

- source の形式を固定するか（検証を入れるか）。調査由来を書き込む経路（導線3 のスキル）を先に作るか
- 検出の担い手。SQL のバッチか、エージェントの導線か、両方か
- 定期実行の担い手（compose にサービスを足す / cron / 人が起動する）
- 検出結果の伝え方。needs_review を立てるのか、別の経路にするのか
