## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
## 位置づけ

設計記録 2.7 の シームレス化 3 点セット（SessionStart / UserPromptSubmit フック、CLAUDE.md テンプレート、ツール呼び出しログ）の一部。設計合意済み・未実装。

## 現状

ログは存在しない。スキーマは 4 テーブル + 1 ビューのみで、server.ts にも db.ts にも記録処理は無い（標準エラーへの起動メッセージ 1 行のみ）。

書き込みの痕跡はデータ自体に残る（created_at / revisions.changed_at / verified_by / verified_at）。読み（検索）の記録は完全にゼロ。

2.7 の主題は MCP を繋いでも触ってくれない問題であり、対策として 3 層（ツール説明 / スキルの手順 / フックで強制）を置いているが、どの層が効いているかを判定する材料が無い。

## 問題の核: 分子は取れるが分母が取れない

設計記録が挙げる 2 つの指標は、サーバ側のログ 1 テーブルでは測れない。

| 測りたいもの | ログで測れる | 測れない |
|---|---|---|
| 検索せず設計を始めたセッション | search_knowledge が 0 回 | 設計を始めたこと自体 |
| 還流ゼロの週 | propose が 0 回 | 還流すべき作業があったか |

MCP サーバに見えるのはツール呼び出しだけで、その外で何が起きたかを知らない。決定的なのは、koto を一度も呼ばなかったセッションはログに 1 行も残らないこと。測りたいのはまさにその無視されたセッションなのに、存在すら現れない。

分母を作るには Claude Code 側のフック（SessionStart / Stop）でセッションの開始・終了を記録する必要がある。3 点セットとしてまとめられているのは正しく、ログ単体では成立しない。設計記録の 1 テーブルで済む という記述は、サーバ側だけを見たときの見立て。

## 決めること

- 何を残すか。ツール名・時刻・成否・件数は無害だが、検索クエリは業務語彙そのもの。Phase 2 の共有 DB では誰が何を検索したかが全員に見える
- どこに残すか。知識 DB に同居させると、性質の違うもの（追記専用・大量・保持期間あり）が知識と同じ日次バックアップに乗る
- 誰が呼んだかを区別するか。created_by は agent 固定。MCP の初期化でクライアント名と版は取れるが、どのリポジトリ・どのマシンかは分からない。複数マシンから同じ DB を見る運用が想定されている
- 失敗時の扱い。ログの書き込み失敗で本処理を止めない（命名警告フックと同じ思想）

## 関連

3 点セットの残り 2 つ（SessionStart / UserPromptSubmit フックスクリプト、CLAUDE.md テンプレート）も未実装。分母を取る話はフック側に属するため、あわせて設計する。
