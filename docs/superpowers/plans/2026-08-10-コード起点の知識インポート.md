# コード起点の知識インポート 実装計画

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 実装コードと git 履歴から業務知識を起こし、使い捨ての下書きを経て koto に draft 投入する導線を、スキルとして用意する。

**Architecture:** コードは書かない。成果物は `skills/koto-code-import/SKILL.md` と、既存の規約ファイルへの symlink、それに追随するドキュメント 3 本。抽出規約は `skills/koto-import/references/知識レコード規約.md` が唯一の正であり、新スキルはそれを symlink で参照して手順(コードの読み方・理由の追い方・下書きの形式)だけを持つ。

**Tech Stack:** Markdown / Claude Code のスキル機構(`.claude/skills/` への symlink)/ koto MCP ツール

設計: `docs/superpowers/specs/2026-08-10-コード起点の知識インポート-design.md`

## Global Constraints

- **この計画にコード変更は無い**。`packages/` と `docker/` には一切触れない。したがって `pnpm run build` / `pnpm test` の実行も不要
- **規約を書き写さない**。何を入れ何を落とすか、title / english_name / aliases の書き方は `知識レコード規約.md` にあり、SKILL.md からは参照するだけ。二重に書けば必ず片方が古くなる
- **スキル本体に特定の事業・言語・フレームワークを書かない**。mindstock が登場してよいのは Task 2(実地検証)の作業中だけで、成果物のファイルには書かない
- コミットメッセージは日本語の Conventional Commits(`docs:` `docs(skill):` など、既存履歴に合わせる)
- 日付表記はこのサイクル全体で `2026-08-10` に揃える(設計文書と対になるため)
- 下書き(`.koto/drafts/`)は対象リポジトリ側に生成される作業ファイル。**koto リポジトリにも対象リポジトリにもコミットしない**

````markdown
# コードから koto への知識インポート

対象リポジトリのコードと git 履歴から業務知識の候補を起こし、下書きにまとめ、ユーザーの確認を経て koto に draft 投入する。読解はこのエージェント自身が行う — 外部の LLM API は呼ばない。

## 前提

- koto MCP(`search_knowledge` / `propose_knowledge` / `propose_update` / `list_contexts`)が接続されていること
- 対象リポジトリのパスと context(領域)名。未指定ならユーザーに確認する
- **1 回の実行 = 1 領域分**。コードベース全体を一度に処理しない。複数領域は領域ごとに繰り返す

## 手順

1. **`references/知識レコード規約.md` を読む**(このスキルと同じディレクトリ)。何を入れ何を落とすか、title / english_name / aliases の書き方はすべてそこが正。判定テスト 2 つ —「業務担当者(非エンジニア)がその言葉を会話で使うか」「コードを書き換えたらこの記述は嘘になるか」— を先に頭に入れる
2. **既存 koto の地図を取る**。`list_contexts` で全 context を把握し、対象 context の既存レコードを `search_knowledge` で引く。何が既にあるかを知らずに書き始めると重複を作る
3. **コトから読む**。エントリポイント(HTTP / RPC ハンドラ、ユースケース、CLI コマンド、定期ジョブ)を先に洗って業務で起きる出来事を列挙し、そこからドメイン型・制約へ降りる。**型定義やテーブル定義から読み始めない** — クラスとテーブルの写経になる
4. **候補ごとに判定テストを適用する**。落とした候補は下書き本体に書かず、末尾の「落とした候補」にまとめる(人が検算できるように)
5. **決定の理由を追う**。「理由の追い方」に従う
6. **既存と突き合わせて 3 分岐を決める**。候補ごとに `search_knowledge` を引き、`新規` / `更新` / `登録しない` を決める。
   - **context で絞り込まない。** 同義語(別の言葉が同じ物)は別の context に居るので、対象 context だけを見ると取りこぼす
   - **英訳を発明する前に引く。** english_name の候補語でも検索する(`search_text` に english_name が含まれるので `resident` で引けば `居住者` が出る)。既存語彙があればそれに合わせる
7. **下書きを書く**。`<対象リポジトリ>/.koto/drafts/<context>.md`。形式は下記。`.koto/` が対象リポジトリの `.gitignore` に無ければ追加をユーザーに案内する(下書きは使い捨てでコミットしない)
8. **ユーザーに提示する**。下書きのパスを示し、未解決の質問を**まとめて**聞く。1 件ずつ聞くと領域全体で数十回になる。ユーザーの直しは下書きファイルに反映してから次へ進む
9. **投入する**。`propose_knowledge` / `propose_update` を呼ぶ。下書きの内容をそのまま渡し、ここで書き直さない
10. **報告する**。登録 / 更新 / 登録しない の件数、未解決の要確認一覧、落とした候補の一覧

## 下書きの形式

1 概念 = 1 ブロック。propose にそのまま転記できる粒度で書く。

```markdown
# 下書き: sales
- 読んだ範囲: src/order/**, migrations/V1__init.sql
- 既存 koto レコード: 12 件(うち approved 5)を突き合わせ済み
- 未解決の質問: 2 件(末尾)

---

## term: 受注  → 更新(既存 id: 0f9c…)
- english_name: sales_order
- aliases: オーダー (synonym), 注文書 (forbidden)
- source: {"kind":"code","ref":"myapp@a1b2c3:src/order/Order.kt","imported_at":"2026-08-10"}
- 既存との差分: 「1 受注は複数の出荷に分かれうる」が既存本文に無い
- review_notes: 要確認: 受注のキャンセル期限が業務上決まっているか

顧客からの注文を受け付けた記録。…本文…

---

## rule: 受注明細の上限行数  → 新規
- source: {"kind":"code","ref":"myapp@a1b2c3:src/order/OrderLines.kt:42"}
- 理由: PR #142「帳票が 2 ページに割れるのを避けるため 20 行で切る」← git 履歴から
- review_notes: (なし)

受注 1 件あたりの明細は 20 行まで。…

---

## 落とした候補

- `OrderRepository`(interface 名)— 実装構造物。業務担当者は使わない
- 「受注テーブルは append-only」— 手段。コードを書き換えたら嘘になる

## 未解決の質問

1. 明細 20 行の根拠は帳票の都合だけか。業務上の上限もあるか
2. 受注のキャンセル期限は決まっているか
```

- 見出し行に **3 分岐の判定**(`新規` / `更新(既存 id)` / `登録しない(理由)`)を書く
- `english_name` を持たない type(`rule` / `decision` / `requirement` / `faq`)では行ごと書かない。規約と食い違う下書きを作らない
- `理由:` 行は git 履歴などから拾えたときだけ書く。拾えなければ `review_notes` に `要確認:` として落とす
- `source.kind` は `"code"`、`ref` にはコミット SHA を含める。後から「どの版のコードを読んだか」が分かるようにするため

## 理由の追い方

コードには「今どう動いているか」しか書かれていない。「なぜそうなっているか」は次の順で降りて探し、埋まらなければ未解決として残す。

1. **git 履歴**。制約値やガードに当たったら `git log -S '<値や識別子>'` と `git blame` で導入コミットを特定し、コミットメッセージと PR 説明(`gh pr view <番号>`)を読む
2. **テスト名・コメント**。「なぜ」が書かれていることがある、コード内の数少ない経路
3. **ユーザーに聞く**。1〜2 で埋まらなかったものを手順 8 でまとめて質問する
4. **`review_notes` に `要確認:` として残す**。推測で埋めない

拾えた理由は body に書き、`source` に導出元(コミット / PR)を残す。出所が残らないと後から再検証できない。

## 注意

- **承認(`approve_knowledge`)はこのスキルから呼ばない。** 投入は draft までで、承認するかどうかはユーザーの判断
- **推測で本文を埋めない。** コードから読めるのは事実(どう動くか)だけ。意図・理由・将来の予定は読めないので `review_notes` に回す
- **実装構造物(テーブル名・クラス名・関数名・enum・コントローラ)は業務知識ではない。** 落とす。規約ファイルに一覧がある
- **特定の言語・フレームワークを前提にしない。** エントリポイントの見つけ方が分からなければ、推測で読み進めずユーザーに聞く
````
