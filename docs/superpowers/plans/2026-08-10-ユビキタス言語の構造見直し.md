> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `english_name` を概念の同一性キーとして機能させ、context 横断の同義語重複を検出し、`aliases`/`forbidden` を検索専用の役割として届く形にする。

**Tech Stack:** TypeScript / Node 24 / pnpm workspace / Postgres 17 + PGroonga + pgvector / vitest / MCP SDK 1.30 / zod 4 / esbuild / biome

```typescript
/**
 * 近似重複の検出: 同名・別名・english_name の完全一致 + 埋め込み類似。
 *
 * context をまたいで見る。同一 context の重複は unique(context, type, title) が防ぐので、
 * ここが受け持つのは「別の言葉が同じ物」(同義語)の方である。多義語(同じ言葉が context で
 * 別物)は english_name が分かれるため、横断しても誤検出にはならない。
 */
export async function findDuplicates(
  title: string,
  englishName: string | null,
  vec: number[] | null,
) {
  const seen = new Map<string, Record<string, unknown>>();

  const byName = await pool.query(
    `select id, title, context, type, status,
            case
              when lower(title) = lower($1) then '同名が一致'
              when exists (select 1 from jsonb_array_elements(aliases) a
                            where lower(a->>'name') = lower($1)
                              and a->>'kind' = 'forbidden') then '禁止表記に一致'
              when exists (select 1 from jsonb_array_elements(aliases) a
                            where lower(a->>'name') = lower($1)) then '別名が一致'
              else 'english_name が一致'
            end as reason
       from knowledge
      where lower(title) = lower($1)
         or exists (select 1 from jsonb_array_elements(aliases) a
                     where lower(a->>'name') = lower($1))
         or ($2::text is not null and lower(english_name) = lower($2))`,
    [title, englishName],
  );
  for (const r of byName.rows) {
    seen.set(r.id, r);
  }

  if (vec) {
    const bySim = await pool.query(
      `select id, title, context, type, status,
              round((1 - (embedding <=> $1::vector))::numeric, 3) as similarity
         from knowledge
        where embedding is not null
        order by embedding <=> $1::vector
        limit 3`,
      [toVectorLiteral(vec)],
    );
    for (const r of bySim.rows) {
      if (Number(r.similarity) >= 0.82 && !seen.has(r.id)) {
        seen.set(r.id, { ...r, reason: `埋め込み類似度 ${r.similarity}` });
      }
    }
  }
  return [...seen.values()];
}
```

```typescript
/**
 * 埋め込みに載せるテキスト。別名も含める —
 * aliases は検索専用の項目であり、キーワード検索でしか効かない状態をなくすため。
 */
export function embeddingSource(input: {
  title: string;
  english_name?: string | null;
  body: string;
  aliases?: Alias[] | null;
}): string {
  const aliasNames = (input.aliases ?? []).map((a) => a.name).join(" ");
  return [input.title, input.english_name ?? "", aliasNames, input.body].filter(Boolean).join(" ");
}

/**
 * 埋め込みを計算し直す変更か。検証レベルのリセット条件とは別物で、aliases はこちらにだけ効く
 * (別名を足しただけで専門家確認を無効にしない)。
 */
export function shouldReembed(changes: Partial<ProposeInput>): boolean {
  return (
    changes.title !== undefined ||
    changes.body !== undefined ||
    changes.english_name !== undefined ||
    changes.aliases !== undefined
  );
}
```

```typescript
 * english_name は title の英訳であり、概念の同一性キー(「同じ english_name = 同じ概念」)。

 * 機能しない。任意にすると実装名を入れる習慣が戻るため、任意ではなく拒否する。
 */
const REQUIRED_TYPES = new Set(["term", "event"]);
const SNAKE_CASE = /^[a-z][a-z0-9_]*$/;

/** 規約違反ならエラーメッセージを返す(問題なければ null) */
export function validateEnglishName(
  type: string,
  englishName: string | null | undefined,
): string | null {
  const value = (englishName ?? "").trim();
  if (!REQUIRED_TYPES.has(type)) {
    return value === ""
      ? null
      : `type=${type} に english_name は登録できません。同一性キーとして機能するのは term / event の 2 つだけです`;
  }
  if (value === "") {
    return `type=${type} には english_name が必要です。title の英訳を小文字 snake_case で書いてください(クラス名・テーブル名・メソッド名などの実装識別子は不可)`;
  }
  if (!SNAKE_CASE.test(value)) {
    return `english_name「${value}」は形式が不正です。小文字 snake_case(^[a-z][a-z0-9_]*$)で、title の英訳を書いてください。実装識別子を写さないこと`;
  }
  return null;
}
```

```typescript
export async function forbiddenAliases(): Promise<ForbiddenAlias[]> {
  const res = await pool.query(
    `select a->>'name' as name, k.title, k.context
       from knowledge k, jsonb_array_elements(k.aliases) a
      where k.status = 'approved'
        and a->>'kind' = 'forbidden'
        and length(a->>'name') >= 2
      order by k.context, k.title`,
```

```typescript
import { type ForbiddenAlias, forbiddenAliases } from "@kukv/koto-core";

/** DB が固まっても編集作業を止めないための上限 */
const DB_TIMEOUT_MS = 3000;

/**
 * PostToolUse の入力から、今回書き込まれたテキストだけを取り出す。
 * ファイル全体を見ないのは、既存コードの禁止表記まで指摘すると
 * 無関係な編集のたびにノイズが出るため。
 */
export function writtenText(hookInput: unknown): string | null {
  const input = hookInput as { tool_name?: string; tool_input?: Record<string, unknown> } | null;
  const toolInput = input?.tool_input;
  if (!toolInput) return null;
  const value =
    input?.tool_name === "Write"
      ? toolInput.content
      : input?.tool_name === "Edit"
        ? toolInput.new_string
        : null;
  return typeof value === "string" ? value : null;
}

export function findForbiddenHits(text: string, forbidden: ForbiddenAlias[]): ForbiddenAlias[] {
  return forbidden.filter((f) => text.includes(f.name));
}

export function formatWarning(hits: ForbiddenAlias[]): string {
  const lines = hits.map(
    (h) => `- 「${h.name}」は禁止表記です。正しくは「${h.title}」(${h.context})`,
  );
  return `koto: 書き込んだ内容に使ってはいけない表記が含まれています。\n${lines.join("\n")}`;
}

/**
 * フック本体。終了コード 2 で stderr の内容がエージェントに返る(PostToolUse なので阻止ではなく指摘)。
 * 知識基盤の警告が作業を止めるのは本末転倒なので、失敗はすべて握りつぶして 0 を返す。
 */
export async function checkNaming(raw: string): Promise<0 | 2> {
  try {
    const text = writtenText(JSON.parse(raw));
    if (!text) return 0;
    const forbidden = await Promise.race([
      forbiddenAliases(),
      new Promise<null>((resolve) => setTimeout(() => resolve(null), DB_TIMEOUT_MS).unref()),
    ]);
    if (!forbidden) return 0;
    const hits = findForbiddenHits(text, forbidden);
    if (hits.length === 0) return 0;
    console.error(formatWarning(hits));
    return 2;
  } catch {
    return 0;
  }
}
```

````markdown
# 知識レコード規約

koto に入れるレコードの書き方。文書インポートでも、ヒアリングからの登録でも、この規約に従う。

## 何を入れ、何を入れないか

**判定テスト: コードを書き換えたらこの記述は嘘になるか。** なるなら「手段」なので入れない。

| 種別 | 例 | 扱い |
|---|---|---|
| 決定 | 表示名は変更できる / 1〜100 文字 | 残す |
| 決定の理由 | なぜ 100 文字なのか | **最優先で残す** |
| 業務上の性質 | 変更しても過去の記録が残る | 残す |
| 手段 | ID 最大の行として求める / append-only テーブル | 落とす |

手段を落とすのは、(a) コードが変わると腐り、エージェントはコードと koto の食い違いを判定できない、(b) コードを読めば常に正確に分かる、(c) 混ざると本当の信号が埋もれる、の 3 つの理由による。

**決定の理由は文書からは原理的に拾えない。** コードや仕様書に「なぜ 100 文字か」は書かれていない。拾えなかったら落とすのではなく、`review_notes` に「要確認: なぜ 100 文字か」と残し、後のヒアリングで埋める。

## term の適用範囲

**判定テスト: 業務担当者(非エンジニア)がその言葉を会話で使うか。** 使わないなら term にしない。

次のものは koto に入れない。別の type に置き換えることもしない。

- テーブル名(`resident_display_names`)
- クラス名・型名(`AuthState`、`ProductBarcodesTable`)
- 関数名・メソッド名(`lookupByJan`、`runGuarded`)
- フィールド名・引数名(`callId`)
- UI コンポーネント・コントローラ(`ReauthController`)
- プロトコル文字列・enum 値(`AppSubprotocol`)

## title(日本語名)

- 日本語の**名詞句**にする。文章にしない
- 英数字と日本語の間にスペースを入れない(`世帯ID` は可、`世帯 ID` は不可)。`(context, type, title)` が複合ユニークのキーなので、表記ゆれはそのまま重複になる
- `term`: 業務で実際に使われている言い方をそのまま使う。実装側の呼び方に寄せない
- `event`: 出来事の名詞化(`受注確定`、`在庫引当`)。「〜する」「〜される」の動詞形にしない
- `rule`: 何についてのルールかが分かる名詞句(`商品名の変更不可`)。`JWT の完全検証は接続確立時の 1 回のみ…` のような文章にしない

## english_name

**`title` の英訳であり、概念の同一性キー**(「同じ english_name = 同じ概念」)。

- **実装識別子を入れない。** クラス名・テーブル名・メソッド名・フィールド名・ファイル名は不可
- 小文字 snake_case(`^[a-z][a-z0-9_]*$`)。`resident`、`order_confirmation`
- 名詞形にする。event も名詞形(`受注確定` → `order_confirmation`)。過去分詞形(`order_confirmed`)は実装側の型の名付け方なので使わない
- **`term` と `event` は必須。`rule` / `decision` / `requirement` / `faq` には付けない**(付けるとツールがエラーを返す)

実装は雑に書かれることもあれば、実装都合で概念と一致しない命名になることもある。english_name を実装に結びつけると、そのときカバーできなくなる。ユビキタス言語は実装から独立して成立していなければならない。

**英訳を発明する前に既存語彙を引く。** `search_knowledge` は english_name も検索対象にしているので、`resident` で引けば `居住者` が出る。同一性キーは「一致したら同じ」しか保証しないため、`resident` と `inhabitant` のようにゆれると検出をすり抜ける。

## aliases

**検索でヒットさせるためだけの項目。** ユビキタス言語としては `title` が正で、成果物の語彙は `title` に統一する。

- `kind: "synonym"` は表記ゆれ・言い換え、`kind: "forbidden"` は使ってはいけない表記
- **alias を独立したレコードとして登録しない。** 「居住者」の別名「住人」を `session/住人` という term にする、という誤りが実際に起きた。alias は知識の情報源ではない
- 統一したい表記があるなら、正を `title` にして、避けたい表記を `forbidden` に入れる。`forbidden` はコード編集時の命名警告フックが突き合わせる

## event の本文

見出し構成は固定する。

```
## 概要
## アクター(誰が起こすか)
## 対象(何に対して)
## 事前条件
## 事後条件(何が成立するか)
## 取消・失敗
## 順序・タイミング
```

文書から読み取れない見出しは本文に「要確認」と書き、`review_notes` にも記載する。

**状態遷移は event に書く。** 状態機械を独立したレコードとして持たず、コトの結果の射影として扱う。

- 状態が変わる event は、`## 事後条件(何が成立するか)` の先頭に次の行を書く

  ```
  - 状態遷移: 受注 / 未確定 → 確定
  ```

- 1 つの event が複数の対象の状態を変えるなら複数行書く
- 失敗・取消で状態が戻るなら `## 取消・失敗` にも同じ書式で書く
- 新規に生まれる場合は `なし → 受付済` と書く
- 状態が変わらない event にはこの行を書かない
- 事前条件に状態を重ねて書かない(遷移前状態がガードを兼ねる)

**状態名は原則 term にしない。** コトの射影を独立レコードにすると二重管理になる。例外は状態そのものに業務上の定義や判断基準がある場合(「与信 NG とはどういう状態か」)で、その場合も遷移の記述は event 側にだけ置く。
````

```markdown
## 追記 2026-08-10: ユビキタス言語の構造の見直し
```
