# ユビキタス言語の構造見直し 設計

> 2026-08-10
> 出所: `docs/フィードバック_2026-08-10_mindstock承認作業.md` の節 2 と 3.1(優先度表の A / C / D / E / F / G と個別項目 4)

## 背景

mindstock の 6 文書を koto に import して 231 件を投入したところ、ユビキタス言語基盤としての構造が機能していないことが分かった。症状は 3 つある。

- `english_name` に実装識別子(クラス名・テーブル名・メソッド名)が入り、概念の英語名になっていない
- 同一概念が context をまたいで 13 グループ重複し、`居住者` と `住人` のように直接矛盾する登録が生まれた
- `aliases` が検索専用のはずが知識の情報源として扱われ、alias が独立レコードに昇格した(上の矛盾はこれが原因)。`forbidden` は 231 件で一度も使われていない

個別の不具合ではなく「ユビキタス言語を統制する」という目的そのものが達成できていないため、規約と実装の両方を見直す。

あわせて、本文規約の議論から派生した「状態遷移をどう持つか」(決定 8)を本設計に含める。フィードバック文書には無い論点だが、event の本文規約に手を入れる以上、同じサイクルで決めた方が規約が二度変わらない。

## 決定

### 1. `english_name` は「概念の同一性キー」にする

**定義**: `title`(日本語名)の英訳。実装識別子(クラス名・テーブル名・メソッド名・フィールド名・ファイル名)は入れない。

実装は雑に書かれることもあれば、実装都合で概念と一致しない命名になることもある。そこに `english_name` を結びつけると、そういうケースが出たときにカバーできない。ユビキタス言語は実装から独立して成立していなければならず、実装名を写すのは依存の向きが逆である。

主目的は**概念の同一性キー** — 「同じ `english_name` = 同じ概念」と見なし、context をまたいだ同義語の乱立を検出する。従来の目的(コード命名の統制)は副次的な効果として残る。この位置づけを選んだのは、埋め込みが既定無効(`EMBEDDING_PROVIDER=none`)である以上、context 横断の重複を検出できる手段が他に無いためである。代償として、英訳のゆれ(`resident` / `inhabitant`)は検出を取りこぼす。

**規約**:

- 小文字 snake_case。同一性キーとして比較するため表記を揺らさない。比較は `lower()` で行う
- 名詞形にする。event も名詞形(`受注確定` → `order_confirmation`)。過去分詞形(`order_confirmed`)は実装側の型の名付け方であり、持ち込むと「実装名を写さない」原則が崩れる
- `term` / `event` は必須。概念そのものに名前が付くため同一性キーが成立する
- `rule` / `decision` / `requirement` / `faq` は**入力を拒否**する。これらの title は命題なので英訳が説明文になり、キーとして機能しない。任意にすると実装名を入れる習慣が戻るため、任意ではなく不可とする

**強制する場所は MCP 層**。DB 制約は入れない。既存 231 件には english_name の無い term / event が 51 件あり、制約を入れると違反する。既存データの是正は別サイクルなので、新規投入だけを規約に合わせる。

検証は `propose_knowledge` と `propose_update` の両方に掛ける。`propose_update` では、`rule` 系のレコードに english_name を渡したらエラーにする(既存値には触れない)。`term` / `event` の english_name を空文字に更新することも拒否する。

**英訳のゆれへの備え: 英訳を発明する前に既存語彙を引かせる。**

同一性キーは「一致したら同じ」という片側しか保証しない。「一致しないから別」は保証しないので、`resident` と `inhabitant` のように英訳がゆれると検出は素通りする。これを埋めるため、koto-import の既存確認手順(手順3)を「title で検索する」から「**title と english_name の候補の両方で検索する**」に変える。

`search_text` には `english_name` が含まれるので、`resident` で引けば `居住者` はヒットする。取りこぼすのは「先に `inhabitant` を思いついてしまった」場合だけであり、エージェントに英訳を発明させず既存語彙を先に見せることで大半は潰れる。残りは棚卸し(今回のスコープ外)で事後に拾う。

### 2. 同一性キーによる重複防止

`findDuplicates` を次のように変える。

- `where context = $2` を外し、title・alias の一致を全 context で見る
- 一致条件に `english_name` の一致を加える(`lower` 比較)
- `reason` に一致の種類を書く(`同名または別名が一致(context 横断)` / `english_name が一致` / `禁止表記に一致`)

設計記録 2.2 が想定したのは「多義語 — 同じ言葉が context によって別物」で、これは `(context, type, title)` の複合ユニークで扱える。実際に起きたのは逆の「同義語 — 別の言葉が同じ物」であり、防御が無かった。多義語(受注の注文 / 発注の注文)は `sales_order` と `purchase_order` に分かれるため、横断化しても誤検出にはならない。

**衝突時の振る舞いは「draft は通し、承認で止める」**。エージェントの書き込みはすべて draft で入るという原則がある以上、propose を失敗させると import が止まる。よって propose は検出結果を `review_notes` と戻り値に載せて登録を通し、`approve_knowledge` の確認ダイアログに同じ `english_name` を持つ他レコード(deprecated 除く)の一覧を出して人に判断させる。ブロックはしない。

承認時に引き直すのは、`review_notes` の重複候補が propose 時点のスナップショットであり、その後に登録された衝突を含まないためである。

### 3. `aliases` は検索用途に限定する

**位置づけ**: `aliases` は検索でヒットさせるためだけの項目。ユビキタス言語としては `title` が正で、成果物の語彙は `title` に統一する。**alias を独立したレコードとして立てない**。`resident/居住者` の alias「住人」が `session/住人` という term になった経路をここで塞ぐ。

この位置づけをツール説明・スキル・設計記録の 3 箇所に明記する。どこにも書かれていなかったことが事故の原因なので、実装だけ直しても再発する。

実装は 3 点。

- **`search_knowledge` の返却に `aliases` を追加**する。現在の返却列には無く、「その語は禁止表記で、正はこれ」を伝える経路が検索結果に存在しない
- **埋め込み対象に alias の name を含める**。あわせて `proposeUpdate` の `contentChanged` に `aliases` を加える(現在は aliases だけ変えても埋め込みが再計算されない)。埋め込みが有効な環境でのみ効くが、「aliases は検索専用」という位置づけと、キーワード検索でしか効かない現状のずれを消す
- **`check-naming` サブコマンドと PostToolUse フック**(次項)

### 4. forbidden を届ける経路をつくる

`forbidden` は設計の柱のひとつだが、登録しても警告が届く経路が無い。`住人` はまさに第一号候補だった。届け先を 3 つ用意する。

- 検索結果(上記 `aliases` の追加でカバー)
- propose 時の検出(`findDuplicates` が kind を問わず alias 一致を見るため、`reason` に「禁止表記に一致」と出す)
- コード編集時の PostToolUse フック(設計記録 2.7 層3)

**フックの形態はバンドルへのサブコマンド追加**とする。Claude Code のフックは独立プロセスとして起動されるため MCP サーバ経由では forbidden を引けず、DB を直接引くかキャッシュを読むかの二択になる。配布物(`koto-mcp.mjs`)を 1 個に保ち、常に最新の forbidden が効く方を採る。編集のたびに Node 起動と DB 接続が入るが、遅ければ後からキャッシュを足せる — 計測前にキャッシュの二重管理を持ち込むのは順序が逆である。

`node koto-mcp.mjs check-naming` が stdin で PostToolUse の入力(JSON)を受け、approved なレコードの forbidden 別名を 1 クエリで引いて突き合わせ、一致したら「その語は禁止表記、正は `<title>`」を stderr に出して exit 2 で Claude に返す。PostToolUse は書き込み後に走るので、これは阻止ではなく指摘である。

突き合わせるのは `Write` / `Edit` の**書き込んだ内容だけ**(`tool_input` の `content` / `new_string`)で、ファイル全体は読まない。既存コードに含まれる禁止表記まで指摘すると、無関係な編集のたびにノイズが出る。

- **フェイルオープン**: DB に繋がらない・エラーが出たときは黙って exit 0。知識基盤の警告が作業を止めるのは本末転倒
- **1 文字の forbidden 語は対象から外す**。日本語には単語境界が無く、1 文字だと部分一致が頻発する

### 5. `term` の適用範囲

**判定テスト: 業務担当者(非エンジニア)がその言葉を会話で使うか**。使わないなら term にしない。

テーブル名・クラス名・関数名・フィールド名・enum・UI コンポーネント・プロトコル文字列は koto に入れない。`表示名履歴`(`resident_display_names`)・`起動分岐`(`AuthState`)・`登録ガード`(`SessionGuard`) はこれで落ちる。別 type に退避させたり専用 context に隔離したりはしない — 結局コードの複写を抱えることになり、コードを読めば常に正確に分かるものを腐る形で持つことになる。

### 6. `title` の規約

event にしか無かった規約を term / rule にも作る。

- 共通: 日本語の**名詞句**。文章にしない。英数字と日本語の間にスペースを入れない(`世帯ID`。`世帯 ID` は不可)。`(context, type, title)` 複合ユニークのキーの一部なので、表記ゆれはそのまま重複の温床になる
- `term`: 業務で実際に使われている言い方をそのまま使う。実装側の呼び方に寄せない
- `event`: 出来事の名詞化(既存規約を維持)
- `rule`: 何についてのルールかが分かる名詞句(`商品名の変更不可`)。`JWT の完全検証は接続確立時の 1 回のみ、以後は…` のような文章にしない

### 7. 抽出規約に「決定と理由 / 手段」の軸を足す

現在の抽出規約は「この業務に固有の概念だけを抽出する」という**除外の基準**しか持たない。出典がコードから起こした資料だったため、規約上は「業務固有」を通過する技術記述が大量に混入した。採否の軸を足す。

| 種別 | 例 | 扱い |
|---|---|---|
| 決定 | 表示名は変更できる / 1〜100 文字 | 残す |
| 決定の理由 | なぜ 100 文字なのか | 最優先で残す |
| 業務上の性質 | 変更しても過去の記録が残る | 残す |
| 手段 | ID 最大の行として求める / append-only テーブル | 落とす |

**判定テスト: コードを書き換えたらこの記述は嘘になるか**。なるなら手段なので落とす。理由は 3 つ — (a) 手段はコードが変わると腐り、エージェントはコードと koto の食い違いを判定できない、(b) 手段はコードを読めば常に正確に分かる、(c) 手段が混ざると本当の信号が埋もれる。

あわせて、**導線1(文書抽出)だけでは決定理由は原理的に拾えない**ことをスキルに明記する。拾えなかった理由は落とさず `review_notes` に「要確認: なぜ 100 文字か」と残し、導線2(ヒアリング)で埋める前提にする。

### 8. 状態遷移は event に従属させ、書き方を定型にする

設計記録 2.3 は「ルールも状態もコトに従属する(『受注ステータス』はコトの結果の射影)」とし、2.2 は「状態遷移図は保守せず relations から都度導出する」としている。この立場は維持する — 状態機械を独立したレコードとして持たない。

ただし現状の event 定型見出しでは**情報は足りるが形が足りない**。「事前条件」「事後条件」は自由文なので、状態の条件(受注が未確定であること)と、それ以外の条件(権限がある・在庫がある)が混ざる。人や LLM が読めば導出できるが、機械的には取り出せず、そもそも状態が書かれないこともある。

スキーマは変えず、**本文の書き方の規約**で埋める。

- 状態が変わる event は、`## 事後条件(何が成立するか)` の先頭に `- 状態遷移: <対象> / <遷移前> → <遷移後>` の行を書く(例: `- 状態遷移: 受注 / 未確定 → 確定`)
- 1 つの event が複数の対象の状態を変えるなら複数行書く
- 失敗・取消で状態が戻るなら、`## 取消・失敗` にも同じ書式で書く
- 遷移前が存在しない(新規に生まれる)場合は `なし → 受付済` と書く
- 状態が変わらない event にはこの行を書かない

これで遷移図の導出に必要な三つ組(対象・遷移前・遷移後)が定型で取れる。事前条件のガードは遷移前状態が兼ねるため、事前条件側に状態を重複して書かない。タイムアウトやバッチによる自動遷移も「支払期限超過」というコトとして同じ形に収まる。

**状態名は原則 term にしない**。コトの射影を独立レコードにすると二重管理になり、event 側とずれる。例外は、状態そのものに業務上の定義や判断基準がある場合(「与信 NG とはどういう状態か」)で、その場合も遷移の記述は event 側にだけ置く。

対象(モノ)との結びつきは既存の relations 規約(コト → モノ = 「対象」)で表現するため、新しいラベルは追加しない。

## 規約の置き場

抽出規約は `skills/koto-import/SKILL.md` に置くが、`english_name` / `title` / `aliases` / term 判定テスト / event の状態遷移の書式は `skills/koto-import/references/知識レコード規約.md` に切り出し、SKILL.md から参照する。将来つくる「インポート元資料を作るスキル」が同じ規約を参照するためで、コピーを作れば必ず食い違う。

## テスト

DB 統合テストとして追加する。

- `findDuplicates` が別 context の同名・同 english_name・forbidden 一致を検出する
- 多義語(`sales_order` / `purchase_order`)は検出しない
- `term` / `event` で english_name 無しの propose がエラーになる
- `rule` で english_name 有りの propose がエラーになる
- `search_knowledge` の結果に `aliases` が含まれる
- `check-naming` が forbidden を検出して exit 2、DB 不通で exit 0
