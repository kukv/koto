# コード起点の知識インポート 設計

> 2026-08-10
> 出所: `docs/フィードバック_2026-08-10_mindstock承認作業.md` の 2.7(優先度表の B)

## 背景

koto に文書を入れる導線は `skills/koto-import/` の 1 本しかない。しかし前回のフィードバックで挙がった問題の多くは、**入れる前の資料の作られ方**に起因していた。

- 資料(`docs/knowledge/*.md`)がコードから起こされたため、決定理由が原理的に含まれない
- 6 つの資料が独立に書かれ、資料間で概念が重複した(同義語 13 グループ)
- 「業務知識」と「実装詳細」の切り分け基準が資料側に無く、技術記述が大量に混入した

つまり事故は「コード → 読み物としての資料 → koto レコード」という**二段抽出**の途中で起きた。前サイクルで規約(`知識レコード規約.md`)と MCP 層の検証は整えたが、コードから起こす経路そのものには手が入っていない。

## 決定

### 1. コード起点の導線を独立したスキルにする

`skills/koto-code-import/` を新設する。`koto-import` と対等な姉妹スキルで、違いは入力だけ。

| | koto-import | koto-code-import |
|---|---|---|
| 入力 | 仕様書・Wiki・議事録 | 対象リポジトリのコード + git 履歴 |
| 中間物 | なし(読みながら直接 propose) | `.koto/drafts/<context>.md`(使い捨て) |
| 理由の扱い | 拾えない前提で review_notes へ | git 履歴を追い、足りなければユーザーに聞く |
| 出口 | `propose_knowledge` / `propose_update` | 同じ |

抽出の中身(何を入れ何を落とすか、title / english_name / aliases の書き方)は **`知識レコード規約.md` が唯一の正**とし、新スキルはそれを symlink で参照する。規約を二重に書かない — 二重に書けば必ず片方が古くなる。

**導線ごとにスキルを増やす構えを取る。** 設計記録 2.6 の導線2(部署ヒアリング)・導線3(調査由来)も、同じ形(規約は共有、スキルは入力の読み方だけを持つ)で後から足せる。今回はコード起点だけを作る。

なお規約ファイルは `skills/koto-import/references/` に置いたままにする。消費者が 3 本以上になれば中立な場所へ移す判断が要るが、今回は移動しない。

**スキルは特定の事業・言語に依存しない。** 対象リポジトリの構造を決め打ちせず、「エントリポイントから読む」という読み方だけを規定する。mindstock が登場するのは実装時の実地検証(節 6)だけで、スキル本体には書かない。

### 2. 1 回の実行 = 1 領域(context)分

コードベース全体を 1 回で処理しない。人がレビューできる量に収まらないためで、実際 mindstock では 26 件の承認作業が 10 件で中断した。

複数領域を扱うときはスキルを繰り返し実行する。領域をまたぐ重複は、後述の「隣接領域も引く」手順で防ぐ。

### 3. 中間物は「レコードの下書き」にし、使い捨てにする

読み物としての資料を挟まない。**下書き = koto レコードの下書きそのもの**とし、抽出を 1 回(コード読解 → 下書き)で終わらせる。

読み物形式(mindstock の `docs/knowledge/*.md`)を採らない理由は 2 つ。(a) 抽出が 2 段残り、そのたびに損失と混入が起きる — 前回の事故がまさにこれ。(b) 下書きを使い捨てにする以上、通しで読める文書としての価値に投資する理由がない。

**使い捨てにする**のは、知識の「正」を koto 側に一本化するため。資料をリポジトリに残すと、koto 側で本文を直しても再 import で戻る二重管理(フィードバック 3.2)を新たに作ることになる。3.2 自体は未解決の別課題だが、この導線で問題を増やさない。

置き場は**対象リポジトリの `.koto/drafts/<context>.md`**。人がエディタで直接直せる場所に置く。コミットはしない(`.gitignore` への追加を案内する)。

### 4. 下書きの形式

1 概念 = 1 ブロック。propose にそのまま転記できる粒度で書く。

```markdown
# 下書き: resident
- 読んだ範囲: server/src/main/kotlin/mindstock/resident/**, V1__init.sql
- 既存 koto レコード: 26 件(うち approved 10)を突き合わせ済み
- 未解決の質問: 3 件(末尾)

---

## term: 居住者  → 更新(既存 id: 0f9c…)
- english_name: resident
- aliases: 住人 (forbidden)
- source: {"kind":"code","ref":"mindstock@a1b2c3:server/.../Resident.kt","imported_at":"2026-08-10"}
- 既存との差分: 「1 居住者は複数の認証プロバイダを持てる」が既存本文に無い
- review_notes: 要確認: 退会・削除を将来提供する予定があるか

mindstock を利用する個人。…本文…

---

## rule: 表示名の文字数制限  → 新規
- source: {"kind":"code","ref":"mindstock@a1b2c3:server/.../DisplayName.kt:18"}
- 理由: PR #142「一覧の折り返しを防ぐため 100 文字で切る」← git 履歴から
- review_notes: (なし)

表示名は 1〜100 文字。…
```

- 見出し行に **3 分岐の判定**(`新規` / `更新(既存 id)` / `登録しない(理由)`)を書く。突き合わせの結果を人が検算できるようにするため
- `english_name` を持たない type(`rule` / `decision` / `requirement` / `faq`)では行ごと書かない。規約と食い違う下書きを作らせない
- `理由:` 行は git 履歴から拾えたときだけ書く。拾えなければ `review_notes: 要確認:` に落とす
- `source.kind` は `"code"` とし、`ref` にはコミット SHA を含める。`source` は自由形式の JSON なのでスキーマ変更は不要
- 末尾に「落とした候補」と「未解決の質問」をまとめる

### 5. 手順

0. **前提確認** — koto MCP 接続、対象リポジトリのパス、context 名(未指定ならユーザーに確認)
1. **規約を読む** — `references/知識レコード規約.md`。判定テスト 2 つ(「業務担当者が会話で使うか」「コードを書き換えたら嘘になるか」)を先に頭に入れる
2. **既存 koto の地図を取る** — `list_contexts` で全 context を把握し、対象 context の既存レコードを引く。**突き合わせは対象 context に閉じない** — 手順 6 の検索は context フィルタを掛けずに全体へ投げる。2.2 の重複は隣の context を見ていなかったことが原因
3. **コトから読む** — エントリポイント(API ハンドラ・RPC・ユースケース)を先に洗って業務の出来事を列挙し、そこからドメイン型・制約へ降りる。型定義から入るとテーブルとクラスの写経になる(2.3 の事故がそれ)
4. **判定テストを適用** — 落とした候補は下書き本体に書かず、末尾にまとめる(人が検算できるように)
5. **理由を追う** — 節 6 の順で降りる
6. **英訳を決める前に既存を引く** — `search_knowledge` で english_name を引き、既存語彙があれば合わせる
7. **下書きを書く** — 各ブロックに 3 分岐の判定を明記する。`.koto/` が対象リポジトリの `.gitignore` に無ければ、追加をユーザーに案内する(下書きは使い捨てでコミットしない)
8. **ユーザーに提示** — 下書きのパスを示し、未解決の質問を**まとめて**聞く。ユーザーの直しは下書きファイルに反映してから次へ進む
9. **投入** — `propose_knowledge` / `propose_update`。下書きの内容をそのまま渡し、ここで再解釈しない
10. **報告** — 登録 / 更新 / 登録しない の件数、未解決の要確認一覧、落とした候補の一覧

**承認(`approve_knowledge`)はこのスキルから呼ばない。** 投入は draft までという既存の原則をそのまま守る。

### 6. 決定の理由をどう埋めるか

コードから理由は原理的に出ない。順に降りて、埋まらなければ未解決として残す。

1. **git 履歴** — 制約値やガードに当たったら `git log -S '<値や識別子>'` と `git blame` で導入コミットを特定し、コミットメッセージと PR 説明(`gh pr view`)を読む
2. **テスト名・コメント** — 「なぜ」が書かれていることがあるコード内の数少ない経路
3. **ユーザーに聞く** — 1〜2 で埋まらなかったものを手順 8 で**まとめて**質問する。1 件ずつ聞くと領域全体で数十回になる
4. **`review_notes: 要確認:` に残す** — 推測で埋めない

拾えた理由は body に書き、`source` に導出元(コミット / PR)を残す。出所が残らないと後から再検証できない。

## 検証

スキルなので自動テストがない。**mindstock の `resident` 領域で実走させ、既存 26 件と突き合わせて**確認する。既存レコードという答え合わせの材料があるためで、mindstock 向けに作るという意味ではない。

| 確認項目 | 判定 |
|---|---|
| `english_name` に実装識別子が入らない | 下書き全ブロックが `^[a-z][a-z0-9_]*$`、型名・テーブル名の直写しが 0 |
| 同義語の重複を作らない | `session` の既存レコードと重なるブロックが「更新」か「登録しない」に分類される |
| 実装構造物を term にしない | 2.3 の 8 件(表示名履歴・登録ガード等)に相当するものが下書きに現れない |
| 手段が混入しない | `rowNumber().partitionBy(...)` のような実装手段の記述が 0 |
| 理由が拾える | git 履歴由来の `理由:` 行が 1 件以上出る |

## 今回やらないこと

- 導線2(部署ヒアリング)・導線3(調査由来)のスキル化。同じ形で後から足せる
- 規約ファイル(`知識レコード規約.md`)の中立な場所への移動。消費者が 3 本以上になってから判断する
- 既存 231 件の是正。規約に沿った再投入は本スキルが動いてから別サイクルで行う
- 再 import の扱い(フィードバック 3.2)。下書きを使い捨てにすることで悪化はさせないが、解決もしない
- `koto-import` の改訂。入力が違うだけで、既存の手順は有効なまま
