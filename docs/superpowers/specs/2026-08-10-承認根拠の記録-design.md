# 設計 — 承認根拠の記録と review_notes の役割分離

> 記録日: 2026-08-10
> 対象: `docs/フィードバック_2026-08-10_mindstock承認作業.md` の 4.1(承認しても要確認が消えない)、4.2(承認根拠が残らない)、4.3(200 文字切り詰めが無言)
> 前提環境: `koto-db-1`(PostgreSQL 18.4 / PGroonga 4.0.8 / pgvector 0.8.6)、knowledge 231 件(approved 10 / draft 219)

フィードバックの優先度表で「高」の #2 / #3 と、同じ領域を触る「低」の #8 をまとめて扱う。節 2 のユビキタス言語構造(A〜G)と 3.x の運用規約は別の設計に分ける。

## 1. 何が壊れているか

### 1.1 承認が「解決した」ことを表せない(4.1)

`approve()` は `needs_review = false` にするだけで `review_notes` に触れない(`packages/core/src/knowledge.ts:233-245`)。結果、承認済みレコードに「要確認: …」が永久に残る。

実測(本番 `koto` の resident コンテキスト、承認済み 10 件):

```
居住者         | approved | 要確認: 「認証情報を持たない薄い集約にする」という設計意図は…
認証プロバイダ | approved | 要確認: ZITADEL 以外のプロバイダを将来追加する想定があるか…
表示名履歴     | approved | 要確認: 過去の表示名を業務上参照する要件があるかは…
```

`get_knowledge` はこれをそのまま返すので、後からこのレコードを読むエージェントは「未解決の確認事項がある」と受け取る。実際には人が見て承認済みである。

### 1.2 承認根拠が一切残らない(4.2)

`reject_knowledge` には `reason`(必須)があり、ツール説明も「この理由自体が後から参照される知識になる」と言う。承認側にそれが無い。

mindstock の承認作業では、承認のたびにコードを読んで裏を取った — `DisplayName.kt` の `requireTrimmedWithin(100)`、`V1__init.sql` の `UNIQUE (provider, subject)`、`allowUnregistered` が 2 箇所しかないこと。**この検証の記録が一切残らない。** 半年後に「この知識は何を根拠に承認されたのか」を辿る手段が無く、再検証は一からになる。

### 1.3 `review_notes` が 4 つの役割を兼ねている(3.3)

現状 `review_notes` に積まれるもの:

| 書き込む経路 | 内容 | 性質 |
|---|---|---|
| `propose`(`knowledge.ts:64-72`) | 業務エキスパートに聞くべき質問 | 未解決 |
| `propose`(`findDuplicates` 経由) | 重複候補の自動検出結果 | 未解決 |
| `proposeUpdate`(`knowledge.ts:126`) | 「更新提案: …」 | 未解決 |
| `reject`(`knowledge.ts:258`) | 「却下(name): reason」 | 判定の記録 |

上 3 つは「まだレビューが要る」を意味し、`needs_review = true` と同期している。4 つ目だけが性質が違う。承認者はこの欄を見ても、何をすべきか(答える / 統合する / 読み流す)を判別できない。

### 1.4 200 文字切り詰めが無言(4.3)

`pendingReviews` は `left(coalesce(review_notes, ''), 200)`(`knowledge.ts:321`)で切るが、省略記号も切り詰めた印も付けない。実際に見えたもの:

> …また登録時に INSERT した行を DB から読み戻さずメモリ上で `Resident` を組み立てて返す実装は、プロジェクト規約(INSERT 後は読み戻

文が途中で切れていることが受け手に伝わらない。同じツールの `total` には「items より多い場合は打ち切られている」という丁寧な注意書きがあるのに、こちらは無言。

## 2. 決めたこと

### 2.1 `review_notes` は「未解決の確認事項」に一本化する

役割を分けるにあたり、3 案を比較した。

| 案 | 内容 | 判断 |
|---|---|---|
| 列を増やさず文字列で処理 | 承認時に `review_notes` を「承認(name): note」で置き換える | **不採用**。未解決事項と判定根拠が同じ欄に混ざる問題(1.3)が残る |
| 2 列に分割 | 「未解決」と「レビュー履歴(追記専用)」を分ける | **不採用**。propose / proposeUpdate / reject / findDuplicates / pendingReviews / get_knowledge の全経路を書き換える必要があり、得られるものに対して変更範囲が大きい |
| **クリア + 判定根拠を別列**(採用) | `review_notes` を未解決専用にし、承認時に `null`。根拠は新列 `verified_note` | 列追加 1 つで済み、「`review_notes` に値がある = 未解決」が一意に決まる |

消えた `review_notes` は `knowledge_revisions` の snapshot に残る(更新トリガが `to_jsonb(old)` を保存する。`001_schema.sql:85-92`)ので、情報自体は失われない。

### 2.2 判定根拠は `verified_by` / `verified_at` と同じ組にする

新列 `verified_note text` を追加し、`verified_by` / `verified_at` / `verified_note` を**常に同じ判定の組**として扱う。3 つが揃って更新され、揃って `null` に戻る。

書き手は `approve` と `setVerification` の 2 経路に限る。この 2 つが `verified_by` / `verified_at` を更新する既存の経路であり、そこに `verified_note` を足すだけで組の一貫性が保てる。

`reject` は現状維持とし、却下理由は `review_notes` への追記のままにする。deprecated は検索の既定対象外で、却下理由は「なぜこのレコードが消えたか」の記録として読まれる。ここを新列へ移すと `verification = 'none'` のまま `verified_by` が埋まるレコードが生まれ、検証軸(none / internal / expert)と判定軸が混ざる。

### 2.3 承認根拠はエージェントが書き、人間がダイアログで見て判定する

`approve_knowledge` / `verify_knowledge` に `note` を**必須**引数として足す。`reject_knowledge` の `reason` が必須であることと対称になる。

elicitation のフォームに自由入力欄を足す案は採らない。設計記録の追記 2026-08-09 にあるとおり、確認者名を自由入力にしたときクライアントのダイアログ上で矢印キーがカーソル移動になり操作が破綻したため選択式に戻した経緯がある。同じ問題を再導入することになる。

代わりに**確認ダイアログのメッセージに `note` を表示する**。エージェントが「何を読んで裏を取ったか」を書き、人間はそれを見て承認するかを決める。人間が根拠に納得しなければダイアログを拒否すればよい。

任意引数にする案も検討したが採らない。`forbidden` 別名が 231 件で 1 件も使われなかったのと同じ理由で、任意にすると書かれなくなる。

## 3. 変更の内容

### 3.1 スキーマ

```sql
alter table knowledge add column verified_note text;
```

`docker/db/init/001_schema.sql`(新規 DB・テスト DB 用の完全スキーマ)と `docker/db/migrations/005_verified_note.sql`(稼働中 DB 向けの差分)の両方を更新する。既存マイグレーション 002 / 003 / 004 は変更しない。

生成列や索引には影響しない(`search_text` は `title` / `english_name` / `koto_alias_names(aliases)` / `body` だけを結合する)。

### 3.2 `packages/core/src/knowledge.ts`

| 関数 | 変更 |
|---|---|
| `approve(id, by, note, expectedUpdatedAt)` | `note` 引数を追加。`review_notes = null`、`verified_note = $note` を set |
| `setVerification(id, level, by, note, expectedUpdatedAt)` | 同上 |
| `proposeUpdate` | 内容変更時に `verified_note` も `null` に戻す(`verified_by` / `verified_at` と同じ `case when $9::boolean` 節に足す) |
| `getKnowledge` | select 句に `verified_note` を追加 |
| `pendingReviews` | 200 字超のとき `…` を付ける |

`reject` / `propose` / `findDuplicates` は変更しない。

`pendingReviews` の切り詰めは SQL 側で行う。`null` を空文字にする現状の挙動は変えない:

```sql
case when length(review_notes) > 200 then left(review_notes, 200) || '…'
     else coalesce(review_notes, '') end as review_notes
```

`search_knowledge` は `review_notes` も `verified_note` も返していない(`search.ts:41-43` の `COLUMNS`)ため変更しない。

### 3.3 `packages/mcp-server/src/`

`elicit.ts` は変更しない。ダイアログのメッセージ文字列は既に呼び出し側(`server.ts`)が組み立てて渡しており(`requireHumanApproval(server, message, target)`)、`note` はそこに含めれば足りる。フォームのスキーマ(確認者の選択)は変えない。

`server.ts`:

| ツール | 変更 |
|---|---|
| `approve_knowledge` | `note: z.string()` を必須で追加。description に「何を読んで裏を取ったかを具体的に書くこと(この記録自体が後から参照される知識になる)」を足す。ダイアログのメッセージを `この知識を承認しますか?\n承認根拠: ${note}` にする |
| `verify_knowledge` | `note: z.string()` を必須で追加。ダイアログのメッセージに検証根拠を出す |
| `get_pending_reviews` | 変更なし(切り詰めの印は core 側で付く) |

### 3.4 マイグレーションと既存データ

**既存データは触らない。** 本番 `koto` の approved 10 件に残る「要確認: …」には、業務エキスパートへの質問として実際にまだ未解決のものが含まれる(「退会・削除機能を将来提供する予定があるか」など)。マイグレーションで機械的に消すと、人の判断が要る情報を失う。

解消したい場合は、対象レコードに対して改めて `approve_knowledge` を実行して `note` を付ける。`approve()` は status を問わず動くため、既に approved のレコードにも適用できる。ただし `get_pending_reviews` は `status = 'draft' or needs_review` でしか拾わないので、この 10 件は一覧に出ない。ID を指定して実行する必要がある。

本番 DB(`koto`、231 件の実データ)への適用はユーザーの判断を仰ぐ。検証は `koto_test` で行う。

## 4. テスト

`packages/core/tests/integration/knowledge.test.ts` に追加する。同ファイルには既に `proposeUpdate` / `setVerification` / `pendingReviews` / `approve` / `reject` の describe があり、それぞれに足す。

| # | 検証内容 | これが無いと通ってしまう退行 |
|---|---|---|
| 1 | 承認すると `review_notes` が `null` になり `verified_note` に note が入る | 4.1 / 4.2 の不具合そのもの |
| 2 | 検証レベル設定でも `verified_by` / `verified_at` / `verified_note` の 3 つが更新され `review_notes` が `null` になる | `setVerification` だけ実装が漏れる |
| 3 | 内容を変える `proposeUpdate` で `verified_note` が `verified_by` / `verified_at` と一緒に `null` に戻る | 旧版に対する承認根拠が新版に残り続ける |
| 4 | 内容を変えない `proposeUpdate`(examples だけ変更など)では 3 つとも残る | 過剰にクリアする実装 |
| 5 | 承認しても `knowledge_revisions` に旧 `review_notes` が残っている | クリアが情報の消失になっていないことの担保 |
| 6 | `get_pending_reviews` が 200 字超の `review_notes` に `…` を付け、ちょうど 200 字では付けない | 4.3。境界を含む |

MCP 層(`note` の必須化・ダイアログのメッセージ)は elicitation がクライアント依存のため統合テストの対象外とし、型検査で担保する。
