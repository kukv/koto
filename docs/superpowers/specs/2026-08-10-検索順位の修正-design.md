# 設計 — 検索順位の修正

> 記録日: 2026-08-10
> 対象: `docs/フィードバック_2026-08-10_mindstock承認作業.md` の 1.1(検索の並び順)と 2.5(b)(`search_text` への JSON キー名混入)
> 検証環境: `koto-db-1`(PostgreSQL 18.4 / PGroonga 4.0.8 / pgvector 0.8.6)、knowledge 231 件(approved 10 / draft 219)、`EMBEDDING_PROVIDER=none`

フィードバックが挙げた 16 項目のうち、本書は検索順位の修正だけを扱う。節 2 のユビキタス言語構造の見直しと、ツール仕様(4.x)は別の設計に分ける。

## 1. 何が壊れているか

### 1.1 実測による原因の特定

フィードバックは「`pgroonga_score()` は Bitmap Heap Scan では 0 を返す」と診断し、対処として `SET enable_bitmapscan = off` を挙げていた。**この診断は誤りで、対処も効かない。** 実測結果:

| 検証 | 結果 |
|---|---|
| Bitmap Heap Scan で score が 0 になる | **再現せず**。`9, 5, 4, 4, 3, 3` と正しく返る |
| 既定経路(approved のみ)で score が 0 になる | **再現**。全行 0 |
| `enable_bitmapscan=off` で直る | **直らない**。既定経路では依然 0 |

真の原因はプランの選択にある。プランナが `status = 'approved'` を見て `idx_knowledge_context` の Index Scan を選び、全文一致条件を Filter に落とす:

```
->  Index Scan using idx_knowledge_context on knowledge
      Index Cond: (status = 'approved'::text)
      Filter: (search_text &@~ '表示名'::text)
```

PGroonga 索引が一度も読まれないため、`pgroonga_score()` に渡せるスコアが存在せず 0 になる。Seq Scan でも同じ。`include_drafts=true`(条件が `status <> 'deprecated'` になる)では PGroonga 索引が使われ、スコアは正常に返る。

つまり**エージェントが使う既定経路だけが壊れている**。

### 1.2 なぜ静かに壊れるか

この不具合には二重の見えにくさがある。

- **全行が同じ値(0)になる**ため、結果は「それらしい順序」で返り続ける。エラーも警告も出ない
- **プラン依存 = データ量依存**である。approved が 10 件しかない現状では `status='approved'` が高選択率なので今のプランになる

後者は 10 万件の合成データで実証した。同じクエリが、行数が増えるとプランを変えてスコアを正しく返すようになる。**黙って直り、黙って再発する**。

`limit 10` / `limit 50` の打ち切りが順不同に効くため、関連知識が静かに欠落する点はフィードバックの指摘どおり。

### 1.3 修正後も残る問題(順位の定義)

プランを直しても、「表示名」の 1 位は `表示名変更`(score 9)で、用語そのものの `表示名` は 2 にしかならない。PGroonga のスコアは出現頻度ベースなので仕様どおりの挙動である。

フィードバックが提案していた「`表示名` 検索で `表示名` が 1 位」という assertion は、プランを直しただけでは通らない。**順位の定義そのものを決める必要がある。**

### 1.4 あわせて直す: `search_text` への JSON キー名混入

生成列が `aliases` を JSON の文字列ごと連結しているため、`kind` / `name` / `synonym` / `forbidden` というキー名が全レコードの索引に入る。実測で `search_text &@~ 'synonym'` が 104 件(別名を 1 つ以上持つレコード全部)にヒットする。

順位ではなくヒット集合の問題であり 1.1 とは別の不具合だが、同時に直す。

## 2. 決定した方針

方針は 2 つに分かれる。**順位の定義**と、**プラン依存の断ち方**である。

### 2.1 順位 — 一致種別を主キー、PGroonga スコアを副キー

| rank | 条件 |
|---|---|
| 0 | `title` がクエリと完全一致(大小文字無視) |
| 1 | `english_name` または `aliases[].name` が完全一致 |
| 2 | `title` がクエリを部分一致で含む |
| 3 | それ以外(本文の一致) |

同一 rank 内は `pgroonga_score` 降順、さらに `updated_at` 降順で安定化する。複数語クエリ(「世帯 招待」)はどの完全一致にも当たらないので全件 rank 3 となり、従来どおりスコア順になる。

ユビキタス言語の辞書として自然な振る舞い(用語を引いたらその用語が 1 位)であることに加え、**順位が静かに壊れない**構造を選んだ。将来またプランが変わって `pgroonga_score` が 0 に落ちても、主キーである一致種別は影響を受けないため、上位の並びは正しいまま残る。今回の不具合が気づかれなかったのは、壊れたときに全部 0 になって「それらしい結果」を返し続けたからである。

### 2.2 プラン依存 — マルチカラム PGroonga 索引で断つ

索引を `pgroonga (search_text, status, context, type)` のマルチカラムにし、`status` / `context` / `type` に `pgroonga_text_term_search_ops_v2`(完全一致用)を指定する。これで絞り込みが PGroonga 索引の Index Cond に入り、プランナが別の索引を選ぶ動機が消える。

```
->  Index Scan using idx_knowledge_fulltext on knowledge k
      Index Cond: ((search_text &@~ '顧客管理') AND (status = 'approved') AND (context = 'rare'))
```

`context` / `type` を含めるのは、SQL が `($n::text is null or context = $n)` の形でも**プランナがパラメータを定数に畳み込む**ため。node-postgres は unnamed statement で実行するので常に custom plan になり、`context` を指定した呼び出しでは `context = 'xxx'` が索引条件の候補になる。含めなければ btree 索引が選ばれる余地が残る。

実測では、2 カラム索引でも `BitmapAnd`(PGroonga 索引 + btree)が選ばれてスコアは正しく返った。しかしこれはコスト見積り次第で変わる。4 カラムにすると単一の Index Scan になり、`context` 未指定(null)の呼び出しでも `search_text` と `status` だけが Index Cond に入る形で正しく動く。索引構築コストは 2 カラムと同等(10 万件で 4.9 秒 / 5.0 秒)。

## 3. 却下した案

### 3.1 CTE MATERIALIZED で絞り込みをプランナから隠す

全文一致と `match_rank` の算出を `with kw as materialized (...)` に閉じ込め、status / context / type の絞り込みを CTE の外に出す案。スキーマ変更が要らない利点がある。当初これを採用しかけたが、**大規模化したときのコストを実測して却下した**。

10 万件の合成データ(平均本文長 241 文字、approved 5%、45% のレコードに別名あり)で、50,001 件がマッチするクエリを 5 回実行した中央値:

| 方式 | 時間 |
|---|---|
| 修正前(順位付けなし) | 17.5ms |
| CTE 案 | **300ms** |
| マルチカラム索引案(順位付けあり) | **29.3ms** |

CTE 案は「絞り込みをプランナから隠す」ために全マッチ行を実体化する。隠した代償がそのままコストになる。エージェントが設計前に何度も引く用途としては重い。

マルチカラム索引案は絞り込みが索引側で済むので、`match_rank` を評価する対象が絞り込み後(5 万マッチ → approved 2,501 件)に減る。CTE も不要になり `order by` に直接書ける。順位付けの対価は 17.5ms → 29.3ms で、絶対値としては実用範囲に収まる。

### 3.2 PGroonga の列ごとの重み付けで順位を作る

`pgroonga_condition(weights => …)` で title を重くする案。重み付けは頻度ベースのままなので「完全一致 > 部分一致」を表現できず、1.3 の問題が残るため却下した。

**マルチカラム索引そのものは 2.2 で採用している**が、用途は絞り込みとプランの安定だけであり、順位付けには使わない。

### 3.3 PGroonga スコアを一切使わない

一致種別だけで順位を決める。プラン依存が原理的に消えるが、本文の関連度が全く効かず、本文ヒット同士を区別できないため却下した。

## 4. 実装

### 4.1 索引とスキーマ

```sql
-- aliases の name だけを連結する(生成列にサブクエリは書けないため IMMUTABLE 関数を挟む)
create function koto_alias_names(jsonb) returns text
  language sql immutable strict as $$
  select coalesce(string_agg(a->>'name', ' '), '')
    from jsonb_array_elements($1) a
$$;
```

生成列の式は `ALTER` で変更できないので、`search_text` 列を drop → add する。既存 231 件は生成列が再計算されるだけで、データは失われない。

**`v_knowledge_approved` が `select *` で `search_text` に依存しているため、そのままでは `drop column` が失敗する**(`cannot drop column search_text ... because view v_knowledge_approved depends on it`)。マイグレーションは次の順で書く:

1. `drop view v_knowledge_approved`
2. `alter table knowledge drop column search_text`
3. `alter table knowledge add column search_text … generated always as (…) stored`
4. 全文索引を張り替える
5. `create view v_knowledge_approved as select * from knowledge where status = 'approved'`

索引はマルチカラムにする:

```sql
create index idx_knowledge_fulltext on knowledge using pgroonga (
  search_text,
  status  pgroonga_text_term_search_ops_v2,
  context pgroonga_text_term_search_ops_v2,
  type    pgroonga_text_term_search_ops_v2
);
```

`idx_knowledge_context` は残す(`list_contexts` が使う)。

`docker/db/init/001_schema.sql`(新規 DB・テスト用の最新スキーマ)と `docker/db/migrations/004_search_text_alias_names.sql`(稼働中 DB 向けの差分)の両方に入れる。002 / 003 と同じ運用。

### 4.2 検索クエリ(`packages/core/src/search.ts`)

CTE を使わず、`match_rank` を `order by` に直接書く。

```sql
select k.id, k.type, k.context, k.title, k.english_name,
       k.status, k.verification, k.needs_review,
       left(k.body, 400) as excerpt,
       pgroonga_score(k.tableoid, k.ctid) as score
  from knowledge k
 where search_text &@~ $1
   and <status 条件>
   and ($2::text is null or context = $2)
   and ($3::text is null or type = $3)
 order by
   case
     when lower(k.title) = lower($1) then 0
     when lower(coalesce(k.english_name, '')) = lower($1)
       or exists (select 1 from jsonb_array_elements(k.aliases) a
                   where lower(a->>'name') = lower($1)) then 1
     when k.title ilike '%' || <$1 のワイルドカードをエスケープ> || '%' then 2
     else 3
   end,
   score desc,
   k.updated_at desc
 limit $4
```

**`status` の条件だけ SQL を 2 通りに分岐する**(`status = 'approved'` / `status <> 'deprecated'`)。現行の `case when $4::boolean then … end` 式のままでは索引条件にならない。

`ilike` に渡すクエリは `%` `_` `\` をエスケープする。エスケープしないと `100%` のようなクエリで rank 2 が誤発火する。ヒット集合ではなく順位だけの問題だが、1 行で防げる。

クエリは JS 側で `trim()` する。前後の空白が残ると rank 0 / 1 の完全一致判定を外す。

`limit` が順位付けの後に効くようになるため、順不同の打ち切りによる知識の欠落も解消される。

なお `jsonb_array_length(k.aliases) > 0` を前置して jsonb の SubPlan を短絡させる案は検証したが、5 回計測の中央値で 27.0ms 対 29.3ms と差が誤差の範囲だったため採らない(当初 35ms → 23ms と見積もったのは、初回コールドを含む 1〜2 回計測の誤りだった)。

### 4.3 ハイブリッド経路(同ファイル)

`kw` の `row_number()` を `order by <match_rank>, score desc` に変更したうえで、**融合後の最終ソートでも `match_rank` を最優先キーにする**。

RRF は順位融合なので、kw 側で 1 位にしてもベクトル側で下位なら融合後に落ちうる。「title 完全一致は必ず上位」を保証するには RRF の外に出す必要がある。RRF の役割は「同じ rank 内の並び」に限定する。

既定は `EMBEDDING_PROVIDER=none` なのでこの経路は動かないが、両経路の挙動を一致させる。

**`kw` の `limit 50` には `order by` を付ける。** 現行コードは `row_number() over (order by …)` を select 句に置くだけで、`limit 50` 自体には順序がない。window 関数は limit より先に評価されるものの、どの 50 行が残るかは順不同なので、上位 50 件を取れている保証がない。`vec` 側も同様。

### 4.4 テスト(`packages/core/tests/integration/search.test.ts`)

1. **順位** — title 完全一致が 1 位、alias 完全一致がそれに次ぎ、本文だけ一致するものが最下位
2. **既定経路(approved のみ)で全ヒットの score が 0 より大きい** — score が 0 に落ちていないかの傍証にはなるが、後述のとおり退行検知としては機能しない
3. **プランの直接検証(主)** — `explain (format json)` で `idx_knowledge_fulltext` が使われ、`status` が Index Cond に入っていることを確認する。**これが唯一の実効的な退行検知**
4. **JSON キー名が索引に入らない** — `search_text &@~ 'synonym'` が 0 件

3 について当初は「テスト DB は行数が本番と違うためプランも違うので、EXPLAIN テストは成立しないのではないか」と考えたが、これは悲観的すぎた。**5 行・ANALYZE なしの状態でも PGroonga 索引が選ばれる**ことを実測で確認している(PGroonga のコスト見積りが極端に低いため)。ただしノード型は状況によって Index Scan にも Bitmap Index Scan にもなるので、**ノード型を固定せず、plan JSON を再帰的に辿って索引名と Index Cond の内容を見る**書き方にすること。

4 は、本文に英単語 `synonym` を含むシードを将来足すと偽陽性で落ちる。シードはテスト側の管理下にあるので許容する。

**訂正(ブランチ全体レビューでの実測により判明):** 当初 2 を「主の防御」、3 を「副」としていたが、これは実測と逆だった。`koto_test` の索引を単一列構成(旧 `idx_knowledge_fulltext(search_text)`)に戻して確認したところ、2 の score > 0 テストは **PASS(検知できない)**、3 の EXPLAIN テストは **FAIL** だった。原因は、単一列索引でもプランナが PGroonga 索引を `BitmapAnd` の片側に使うため score が 0 に落ちないこと。本番相当の 239 行でも score は `1, 1, 4` のように返った。つまり **score > 0 テストは索引構成の退行を検知できず、実際に守っているのは 3 の EXPLAIN テストだけ**である。score > 0 テストは(score が本当に 0 になるような、より深刻な壊れ方に対する)保険として残すが、退行検知の主防御という位置づけは誤りなので訂正する。

## 5. 承知のうえで残す限界

- 完全一致による順位付けは単一語クエリでのみ効く。複数語クエリは従来どおりスコア順
- `include_drafts=true` の経路は `status <> 'deprecated'` が索引条件にならず Filter になる。PGroonga 索引自体は使われるためスコアは正しく返るが、対象行数が多いぶん遅い(10 万件・5 万マッチで 174ms)。既定経路ではないため許容する
- マルチカラム索引は書き込み時のコストが単一列より高い。10 万件の索引構築で約 5 秒、`status` を 1 行更新して 27〜83ms(revisions トリガ込み)。承認は 1 件ずつなので実用上の影響は小さい
- 検証はすべて PGroonga 4.0.8 / PostgreSQL 18.4 でのみ行った。`pgroonga_text_term_search_ops_v2` の挙動が他バージョンで同じである保証はない
- **プラン依存を完全には断てない。** 4 カラム索引はプランナが PGroonga 索引を選ぶ動機を強めるだけで、`idx_knowledge_context` を残す以上、コスト見積り次第で別の選択はありうる。最終的な防御は 2.1 の match_rank(スコアが 0 に落ちても上位の並びが崩れない)であり、索引設計はその手前の一段にすぎない
