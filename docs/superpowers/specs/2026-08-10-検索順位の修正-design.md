# 設計 — 検索順位の修正

> 記録日: 2026-08-10
> 対象: `docs/フィードバック_2026-08-10_mindstock承認作業.md` の 1.1(検索の並び順)と 2.5(b)(`search_text` への JSON キー名混入)
> 検証環境: `koto-db-1`(PostgreSQL 18.4 / PGroonga 4.0.8 / pgvector 0.8.6)、knowledge 231 件(approved 10 / draft 219)、`EMBEDDING_PROVIDER=none`

フィードバックが挙げた 16 項目のうち、本書は検索順位の修正だけを扱う。節 2 のユビキタス言語構造の見直しと、ツール仕様(4.x)は別の設計に分ける。

## 1. 何が壊れているか

### 1.1 実測による原因の特定

フィードバックは「`pgroonga_score()` は Bitmap Heap Scan では 0 を返す」と診断し、対処として `SET enable_bitmapscan = off` を挙げていた。**この診断は誤りで、対処も効かない。** 実測結果:

| 検証 | 結果 |
|---|---|
| Bitmap Heap Scan で score が 0 になる | **再現せず**。`9, 5, 4, 4, 3, 3` と正しく返る |
| 既定経路(approved のみ)で score が 0 になる | **再現**。全行 0 |
| `enable_bitmapscan=off` で直る | **直らない**。既定経路では依然 0 |

真の原因はプランの選択にある。プランナが `status = 'approved'` を見て `idx_knowledge_context` の Index Scan を選び、全文一致条件を Filter に落とす:

```
->  Index Scan using idx_knowledge_context on knowledge
      Index Cond: (status = 'approved'::text)
      Filter: (search_text &@~ '表示名'::text)
```

PGroonga 索引が一度も読まれないため、`pgroonga_score()` に渡せるスコアが存在せず 0 になる。Seq Scan でも同じ。`include_drafts=true`(条件が `status <> 'deprecated'` になる)では PGroonga 索引が使われ、スコアは正常に返る。

つまり**エージェントが使う既定経路だけが壊れている**。

### 1.2 なぜ静かに壊れるか

この不具合には二重の見えにくさがある。

- **全行が同じ値(0)になる**ため、結果は「それらしい順序」で返り続ける。エラーも警告も出ない
- **プラン依存 = データ量依存**である。approved が 10 件しかない現状では `status='approved'` が高選択率なので今のプランになる。承認が進めばプランは反転しうる。つまり黙って直り、黙って再発する

`limit 10` / `limit 50` の打ち切りが順不同に効くため、関連知識が静かに欠落する点はフィードバックの指摘どおり。

### 1.3 修正後も残る問題(順位の定義)

プランを直しても、「表示名」の 1 位は `表示名変更`(score 9)で、用語そのものの `表示名` は 2 にしかならない。PGroonga のスコアは出現頻度ベースなので仕様どおりの挙動である。

フィードバックが提案していた「`表示名` 検索で `表示名` が 1 位」という assertion は、プランを直しただけでは通らない。**順位の定義そのものを決める必要がある。**

### 1.4 あわせて直す: `search_text` への JSON キー名混入

生成列が `aliases` を JSON の文字列ごと連結しているため、`kind` / `name` / `synonym` / `forbidden` というキー名が全レコードの索引に入る。実測で `search_text &@~ 'synonym'` が 104 件(別名を 1 つ以上持つレコード全部)にヒットする。

順位ではなくヒット集合の問題であり 1.1 とは別の不具合だが、同時に直す。

## 2. 決定した方針

**順位は「一致種別」を主キー、PGroonga スコアを副キーとする。**

| rank | 条件 |
|---|---|
| 0 | `title` がクエリと完全一致(大小文字無視) |
| 1 | `english_name` または `aliases[].name` が完全一致 |
| 2 | `title` がクエリを部分一致で含む |
| 3 | それ以外(本文の一致) |

同一 rank 内は `pgroonga_score` 降順、さらに `updated_at` 降順で安定化する。複数語クエリ(「世帯 招待」)はどの完全一致にも当たらないので全件 rank 3 となり、従来どおりスコア順になる。

この構造を選んだ理由は、ユビキタス言語の辞書として自然な振る舞い(用語を引いたらその用語が 1 位)であることに加え、**順位が静かに壊れないこと**にある。将来またプランが変わって `pgroonga_score` が 0 に落ちても、主キーである一致種別は影響を受けないため、上位の並びは正しいまま残る。今回の不具合が気づかれなかったのは、壊れたときに全部 0 になって「それらしい結果」を返し続けたからである。

検討して採らなかった案:

- **マルチカラム PGroonga 索引 + 列ごとの重み** — `search_text` 生成列をやめ `pgroonga_condition(weights => …)` で title を重くする。JSON キー名混入も同時に解消し、フィルタ列を索引に含めればプラン依存自体が消える。採らなかったのは、重み付けは頻度ベースのままなので「完全一致 > 部分一致」を表現しきれず、1.3 の問題が残るため
- **PGroonga スコアを一切使わない** — 一致種別だけで順位を決める。プラン依存が原理的に消えるが、本文の関連度が全く効かず、本文ヒット同士を区別できない

## 3. 実装

### 3.1 フォールバック経路(`packages/core/src/search.ts`)

全文一致と `match_rank` の算出を `CTE ... AS MATERIALIZED` に閉じ込め、status / context / type の絞り込みを CTE の外に出す。これで絞り込み条件がプランに干渉できなくなり、PGroonga 索引が必ず使われる。

```sql
with kw as materialized (
  select id,
         pgroonga_score(tableoid, ctid) as score,
         case
           when lower(title) = lower($1) then 0
           when lower(coalesce(english_name, '')) = lower($1)
             or exists (select 1 from jsonb_array_elements(aliases) a
                         where lower(a->>'name') = lower($1)) then 1
           when title ilike '%' || $1 || '%' then 2
           else 3
         end as match_rank
    from knowledge
   where search_text &@~ $1
)
select k.id, k.type, k.context, k.title, k.english_name,
       k.status, k.verification, k.needs_review,
       left(k.body, 400) as excerpt,
       kw.score
  from kw join knowledge k on k.id = kw.id
 where <FILTERS>
 order by kw.match_rank, kw.score desc, k.updated_at desc
 limit $5
```

`limit` が順位付けの後に効くようになるため、順不同の打ち切りによる知識の欠落も解消される。

**CTE 内に件数上限は置かない。** 置けば順不同の打ち切りを再導入することになる。231 件規模では非問題であり、大規模化したときに改めて設計する。

### 3.2 ハイブリッド経路(同ファイル)

`kw` の `row_number()` を `order by match_rank, score desc` に変更したうえで、**融合後の最終ソートでも `match_rank` を最優先キーにする**。

RRF は順位融合なので、kw 側で 1 位にしてもベクトル側で下位なら融合後に落ちうる。「title 完全一致は必ず上位」を保証するには RRF の外に出す必要がある。RRF の役割は「同じ rank 内の並び」に限定する。

既定は `EMBEDDING_PROVIDER=none` なのでこの経路は動かないが、両経路の挙動を一致させる。`kw` の `limit 50` は `match_rank` 順で効くようになるため意味を持つ。

### 3.3 `search_text` の生成式

`aliases` の `name` だけを連結する。生成列にサブクエリは書けないため IMMUTABLE 関数を挟む:

```sql
create function koto_alias_names(jsonb) returns text
  language sql immutable strict as $$
  select coalesce(string_agg(a->>'name', ' '), '')
    from jsonb_array_elements($1) a
$$;
```

生成列の式は `ALTER` で変更できないので、列を drop → add する。`idx_knowledge_fulltext` も張り直す。既存 231 件は生成列が再計算されるだけで、データは失われない。

`docker/db/init/001_schema.sql`(新規 DB・テスト用の最新スキーマ)と `docker/db/migrations/004_search_text_alias_names.sql`(稼働中 DB 向けの差分)の両方に入れる。002 / 003 と同じ運用。

### 3.4 テスト(`packages/core/tests/integration/search.test.ts`)

1. **順位** — title 完全一致が 1 位、alias 完全一致がそれに次ぎ、本文だけ一致するものが最下位
2. **既定経路(approved のみ)でも順位が保たれる** — 今回の不具合の直撃点
3. **プランの直接検証** — `explain (format json)` で CTE 内が `idx_knowledge_fulltext` を使っていることを確認する
4. **JSON キー名が索引に入らない** — `search_text &@~ 'synonym'` が 0 件

3 は実装依存で脆いという批判はありうる。それでも入れるのは、この不具合がプラン依存で静かに壊れる性質だからである。テスト DB は行数が本番と違うためプランも変わり、順位 assertion だけでは再発をすり抜ける。

## 4. 承知のうえで残す限界

- CTE が全マッチ行を返すため、knowledge が大規模化すると全文一致の結果セットが大きくなる
- 完全一致による順位付けは単一語クエリでのみ効く。複数語クエリは従来どおりスコア順

## 5. 本書が扱わないもの
