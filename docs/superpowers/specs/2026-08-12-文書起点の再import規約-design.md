# 設計 — 文書起点の再 import 規約

> 記録日: 2026-08-12
> 対象: `docs/フィードバック_2026-08-10_mindstock承認作業.md` の 3.2(知識の「正」がどこにあるかが決まっていない)
> 前提環境: knowledge 251 件(2026-08-12 実数確認: approved 10 / draft 238 / deprecated 3)、`skills/koto-import/` と `skills/koto-code-import/` の 2 導線が稼働

フィードバックの優先度表で「中」の #5。コード起点は先行して決着済み(設計記録 224 行)なので、本設計は**文書起点だけ**を扱う。

## 1. 何が決まっていないか

### 1.1 knowledge の「正」がどこにあるか

mindstock で import した 26 件の `source.ref` はすべて `docs/knowledge/resident.md`(mindstock 側のファイル)。koto 側で本文から実装詳細を削って承認しても、**その文書を再 import すれば同じ記述が戻ってくる**。

フィードバック 3.2 は 2 つの道を並べていた。

- koto が正なら、import 後に元文書を捨てるか「import 済み・以後 koto が正」と印を付ける運用が要る
- 文書が正なら、koto での修正は無意味なので、修正を文書側へ還流させる導線が要る

どちらも決まっていない。

### 1.2 2 回目以降の取り込みで何をすべきかが書かれていない

設計記録 2.6 は初期投入の導線を 3 つ定義するが、再取り込みの扱いが無い。`skills/koto-import/SKILL.md` の手順 4 は 3 行しかない。

```
4. 候補ごとに `search_knowledge` で既存知識を確認し、3分岐する:
   - ヒットなし → `propose_knowledge`
   - 既存と矛盾・不足 → `propose_update`
   - 内容が一致 → 登録しない(重複を作らない)
```

`include_drafts` の指定が無く、全文を読む指示も無く、2 回目以降であることを意識した記述が無い。同じ領域を扱う `skills/koto-code-import/` の手順 6 には、これらがすべて書かれている。

### 1.3 実害の一段は既に塞がっている

「再 import で技術記述が戻る」の直接の原因は、抽出規約が採否の軸を持たず実装詳細を通していたことだった。ここは PR #30 で「決定と理由は残し、手段は落とす」が入り、一段は塞がっている。

残っているのは、**人が承認の場で意図して落とした記述を、文書に書いてあるという理由で書き戻さない**という規則そのものが、どこにも無いこと。

## 2. 決めたこと

### 2.1 knowledge の正は koto 側に置く

文書は**取り込みの入力**であって同期対象ではない。再 import は「文書側に新しい情報があるか」を見る行為であり、「文書の内容で koto を上書きする」行為ではない。

コード起点の決着(設計記録 224 行「知識の『正』は koto 側に置く」)と揃う。導線が増えても、正の所在が導線ごとに違うと運用が破綻するため。

**元文書に「import 済み」の印を付ける運用は採らない。** 正が koto 側にあると決めた以上、文書側の状態を管理する必要がない。印を付ける運用は、印の付け忘れという新しい失敗モードを増やすだけになる。

**koto の修正を文書へ還流させる導線も作らない。** 文書は組織の別の目的(読み物・仕様の伝達)で生き続けるものであり、koto の都合で書き換える対象ではない。文書と koto の記述がずれることは許容する。

### 2.2 手順 4(既存との突き合わせ)を `koto-code-import` の手順 6 に揃える

再 import の本体は「既存を正しく見つけられるか」に尽きる。見つけ損ねればそれは重複の新規作成になり、3 分岐そのものが機能しない。

| 足すこと | 無いと起きること |
|---|---|
| `include_drafts: true` で引く | 前回自分が入れた draft が見えず二重に作る(既定は承認済みのみが対象で、このスキルの投入物はすべて draft のまま溜まる) |
| `context` で絞らない | 同義語(別の言葉が同じ物)は別の context に居るので取りこぼす |
| 「内容が一致」の判定前に `get_knowledge` で全文を読む | `search_knowledge` が返すのは抜粋。抜粋だけで一致と判断すると差分を落とす |
| english_name の候補語でも引く | 英訳を先に発明して同義語の重複を作る(`search_text` に english_name が含まれるので `resident` で引けば `居住者` が出る) |

これらは初回 import でも正しい手順であり、再 import 専用の分岐ではない。

### 2.3 差分の扱いを status で分ける

抽出規約(2 つの判定テスト)を先に通したうえで、なお文書と koto の記述が食い違うときの扱い。**文書にあって koto に無い記述と、文書と koto が矛盾する記述の両方**を指す(既存の 3 分岐が「矛盾・不足」と呼んでいたもの)。

| 対象 | 扱い |
|---|---|
| `draft` | 本文を直す `propose_update`(`body` を渡す) |
| `approved` | `propose_update` を **`note` だけで呼ぶ**。`body` を渡さない |

`propose_update` は `id` と `note` だけで呼べる。`packages/core/src/knowledge.ts:198-240` の `contentChanged` は `title` / `body` / `english_name` のいずれかが渡されたときだけ真になるため、`note` だけの呼び出しでは:

- 本文はそのまま
- `verification` / `verified_by` / `verified_at` / `verified_note` は保たれる
- `needs_review = true` が立つ
- `review_notes` に `更新提案: <note>` が積まれる

承認は人が中身を見て通した判定である。文書に書いてあるという理由だけで上書きすると、その判定が黙って消える。一方で「承認済みには一切触れない」にすると、文書が更新されて本当に新しい情報があっても届かなくなる。本文を守りつつ人には届く形として、この非対称を採る。

矛盾の場合、どちらが正しいかはエージェントには判定できない(文書が古いのか、koto が古いのか、業務が変わったのかが読めない)。`note` には**どちらが正しいかの結論ではなく、文書側の記述と koto 側の記述を両方**書く。判定は承認者が行う。

`note` だけの提起を受けて本文を直すのは、承認者がレビューの場で判断したときであり、そのときだけ `body` 付きの `propose_update` を使う。この経路は承認ゲートを通らない(`propose_update` は `status` を変えないので、書き換えた瞬間から approved として検索に出る)。`body` を渡すので `contentChanged` が真になり、`verification` と `verified_note` はリセットされる(上記)。塞がっている経路ではなく、この非対称の裏側として存在する。

### 2.4 承認時の `note` に「意図して落とした記述」も書く

2.3 だけでは、人が「この記述は要らない」と判断しても次の再 import で同じ差分がまた提起される。承認は `review_notes` を `null` にする(PR #29)ので、判断の跡が残らないため。

判断の置き場所を `verified_note` にする。`approve_knowledge` の `note`(PR #29 で必須化済み)は「何を読んで裏を取ったか」を書く欄だが、ここに**文書から意図して落とした記述**も書く規約を足す。`verified_note` は `getKnowledge` が返す(`knowledge.ts:246`)ので、再 import 時に読める。そこに落としたと書かれている記述は再提起しない。

スキーマ変更も引数追加も要らない。専用の列やフィールドを新設する案は採らない — マイグレーションとツール引数の追加に見合うほどの問題ではなく、`verified_note` が既に「その承認で人が何を考えたか」を残す欄として存在する。

**既存 251 件(2026-08-12 実数確認)の `verified_note` には書かれていない。** 埋め直しもしない(内容を知っているのは承認した人だけで、機械的には復元できない)。効くのは今後の承認分からになる。

**既知の限界: `verified_note` は蓄積されず、置換される。** `approve`(再承認)・`setVerification`(検証レベル設定)はいずれも `verified_note` を全置換し、`body` 付きの `propose_update` は内容変更時に `null` に戻す(`packages/core/src/knowledge.ts`)。この規約の定常サイクルは「再取り込み → `note` だけの `propose_update` → `needs_review` → 人が再承認」であり、その再承認のたびに前回の「落とした記述」は承認者が書き写さない限り消える。しかも承認の確認ダイアログ(`packages/mcp-server/src/elicit.ts` の `reviewTarget` / `server.ts`)は既存の `verified_note` を表示しないため、承認者は自分が何を上書きしようとしているのかを見ないまま上書きする。引き継ぎは承認者の手作業に依存する。ダイアログに既存の `verified_note` を出すところまでは今回の範囲に含めない。

### 2.5 `source` は初回のまま残す

`propose_update` に `source` を渡す引数は無い。再 import しても `source` は初回の文書パスと日付のまま残る。

これを変えない。新しい出典は `note` に添える(`skills/koto-code-import/` の手順 9 が更新時に `source` を `note` へ混ぜているのと同じ扱い)。`propose_update` に `source` 引数を足す案は採らない — 出典が「初回にどこから来たか」を指すのは妥当であり、更新のたびに上書きすると最初の出所が失われる。

### 2.6 複合ユニーク違反は検索漏れのサイン

`docker/db/init/001_schema.sql:58` の `unique (context, type, title)` により、既存と同じ組み合わせで `propose_knowledge` を呼ぶと Postgres の 23505 がそのままツールエラーとして返る(`propose()` は素の insert)。

3 分岐を先に正しくやれば起きない。**起きたということは「既存があるのに検索で見つけられなかった」**ということなので、`search_knowledge` で引き直して `propose_update` に回す。エラーを握り潰す実装や、`on conflict` を足す実装は入れない — 見つけられなかった事実自体が、突き合わせが不十分だったという信号である。

## 4. 検証

スキルとドキュメントの変更なので自動テストの対象外。`skills/koto-code-import/` を作ったときと同じく、**素の読者による実走**で確かめる。

スキルを知らないエージェントに、既に koto へ import 済みの文書(`resident` コンテキストの出典文書)をもう一度取り込ませ、次を判定する。

| # | 判定項目 | これが落ちると |
|---|---|---|
| 1 | 既存レコードを全件見つけられるか(`include_drafts` を指定し、context で絞らず引くか) | 重複を新規作成する。再 import が機能しない |
| 2 | 承認済みレコードの本文を書き換えないか(`note` だけの `propose_update` になるか) | 人の承認判定が黙って消える |
| 3 | `verified_note` に落としたと書かれた記述を再提起しないか | 2.4 が効かず、毎回同じ差分が出る |
| 4 | 「内容が一致」と判定する前に `get_knowledge` を呼ぶか | 抜粋だけで判断して差分を落とす |

判定 3 は、対象レコードの `verified_note` に落とした記述が書かれている状態を先に作ってから実走する必要がある。本番 `koto` の approved 10 件には書かれていないため、検証用に 1 件を `approve_knowledge` で書き足すか、`koto_test` に状況を作る。**本番 DB の既存レコードを検証のために書き換えない。**

落ちた項目があれば SKILL.md を直して実走からやり直す。

## 5. 本設計が扱わないもの

- **`skills/koto-code-import/` は変更しない。** 同スキルの「相手が承認済みでも `更新` にしてよい」は、既存レコードが規約違反(english_name に実装識別子が入っている等)のときに直す話であり、文書由来の差分を足す話とは別の場面を指す。2.3 の非対称はこれを否定しない
- `koto-import` に規約違反の既存レコードを直す手順を足すこと。3.2 の範囲外
- 既存 251 件の `verified_note` を埋め直すこと(2.4)
- `propose_update` への `source` 引数の追加(2.5)
- 文書側の更新検知(前回 import 時点からの差分を機械的に出す等)。文書は入力であって同期対象ではないという 2.1 の帰結
- フィードバックの残項目: 4.4 owner 未設定コンテキストでの承認警告、4.5 レビューをセッションとして扱う概念
