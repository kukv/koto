# 知識レコード規約

koto に入れるレコードの書き方。文書インポートでも、ヒアリングからの登録でも、この規約に従う。

## 何を入れ、何を入れないか

**判定テスト: コードを書き換えたらこの記述は嘘になるか。** なるなら「手段」なので入れない。

| 種別 | 例 | 扱い |
|---|---|---|
| 決定 | 表示名は変更できる / 1〜100 文字 | 残す |
| 決定の理由 | なぜ 100 文字なのか | **最優先で残す** |
| 業務上の性質 | 変更しても過去の記録が残る | 残す |
| 手段 | ID 最大の行として求める / append-only テーブル | 落とす |

手段を落とすのは、(a) コードが変わると腐り、エージェントはコードと koto の食い違いを判定できない、(b) コードを読めば常に正確に分かる、(c) 混ざると本当の信号が埋もれる、の 3 つの理由による。

**決定の理由は文書からは原理的に拾えない。** コードや仕様書に「なぜ 100 文字か」は書かれていない。拾えなかったら落とすのではなく、`review_notes` に「要確認: なぜ 100 文字か」と残し、後のヒアリングで埋める。

## term の適用範囲

**判定テスト: 業務担当者(非エンジニア)がその言葉を会話で使うか。** 使わないなら term にしない。

次のものは koto に入れない。別の type に置き換えることもしない。

- テーブル名(`resident_display_names`)
- クラス名・型名(`AuthState`、`ProductBarcodesTable`)
- 関数名・メソッド名(`lookupByJan`、`runGuarded`)
- フィールド名・引数名(`callId`)
- UI コンポーネント・コントローラ(`ReauthController`)
- プロトコル文字列・enum 値(`AppSubprotocol`)

## title(日本語名)

- 日本語の**名詞句**にする。文章にしない
- 英数字と日本語の間にスペースを入れない(`世帯ID` は可、`世帯 ID` は不可)。`(context, type, title)` が複合ユニークのキーなので、表記ゆれはそのまま重複になる
- `term`: 業務で実際に使われている言い方をそのまま使う。実装側の呼び方に寄せない
- `event`: 出来事の名詞化(`受注確定`、`在庫引当`)。「〜する」「〜される」の動詞形にしない
- `rule`: 何についてのルールかが分かる名詞句(`商品名の変更不可`)。`JWT の完全検証は接続確立時の 1 回のみ…` のような文章にしない

## english_name

**`title` の英訳であり、概念の同一性キー**(「同じ english_name = 同じ概念」)。

- **実装識別子を入れない。** クラス名・テーブル名・メソッド名・フィールド名・ファイル名は不可
- 小文字 snake_case(`^[a-z][a-z0-9_]*$`)。`resident`、`order_confirmation`
- 名詞形にする。event も名詞形(`受注確定` → `order_confirmation`)。過去分詞形(`order_confirmed`)は実装側の型の名付け方なので使わない
- **`term` と `event` は必須。`rule` / `decision` / `requirement` / `faq` には付けない**(付けるとツールがエラーを返す)

実装は雑に書かれることもあれば、実装都合で概念と一致しない命名になることもある。english_name を実装に結びつけると、そのときカバーできなくなる。ユビキタス言語は実装から独立して成立していなければならない。

**英訳を発明する前に既存語彙を引く。** `search_knowledge` は english_name も検索対象にしているので、`resident` で引けば `居住者` が出る。同一性キーは「一致したら同じ」しか保証しないため、`resident` と `inhabitant` のようにゆれると検出をすり抜ける。

## aliases

**検索でヒットさせるためだけの項目。** ユビキタス言語としては `title` が正で、成果物の語彙は `title` に統一する。

- `kind: "synonym"` は表記ゆれ・言い換え、`kind: "forbidden"` は使ってはいけない表記
- **alias を独立したレコードとして登録しない。** 「居住者」の別名「住人」を `session/住人` という term にする、という誤りが実際に起きた。alias は知識の情報源ではない
- 統一したい表記があるなら、正を `title` にして、避けたい表記を `forbidden` に入れる。`forbidden` はコード編集時の命名警告フックが突き合わせる

## event の本文

見出し構成は固定する。

```
## 概要
## アクター(誰が起こすか)
## 対象(何に対して)
## 事前条件
## 事後条件(何が成立するか)
## 取消・失敗
## 順序・タイミング
```

文書から読み取れない見出しは本文に「要確認」と書き、`review_notes` にも記載する。

**状態遷移は event に書く。** 状態機械を独立したレコードとして持たず、コトの結果の射影として扱う。

- 状態が変わる event は、`## 事後条件(何が成立するか)` の先頭に次の行を書く

  ```
  - 状態遷移: 受注 / 未確定 → 確定
  ```

- 1 つの event が複数の対象の状態を変えるなら複数行書く
- 失敗・取消で状態が戻るなら `## 取消・失敗` にも同じ書式で書く
- 新規に生まれる場合は `なし → 受付済` と書く
- 状態が変わらない event にはこの行を書かない
- 事前条件に状態を重ねて書かない(遷移前状態がガードを兼ねる)

**状態名は原則 term にしない。** コトの射影を独立レコードにすると二重管理になる。例外は状態そのものに業務上の定義や判断基準がある場合(「与信 NG とはどういう状態か」)で、その場合も遷移の記述は event 側にだけ置く。
